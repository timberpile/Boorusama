## Problem and expected behavior

Separate toolbar Copy and Share actions make payload discovery inconsistent. Every default post toolbar, including Pixiv, should expose one Share action that opens the same sheet, with Media and Links segments and explicit payload actions.

## Acceptance criteria

- Exactly one toolbar Share action and no separate Copy action; sheet title, tooltip, and accessible name are “Share”. The sheet defaults to Media, remembers its selected segment only while open, and switching segments makes no network request.
- Every available Media and Links row shows Copy and Share. Image and Original copy image bytes and share a prepared file; Video copies the exact resolved video link as text and shares a prepared file; Post ID uses plain text; Booru, Source, and Image links use link sharing. Unavailable rows keep both controls visible but disabled, with localized “Unavailable”. GIF is reserved for item 28.
- Image uses the viewer-selected variant and remains available with a valid URL regardless of cache state. Cache hit and cancellable cache miss produce the same payload. Original resolves the exact upstream original and remains a separate row even when it equals Image.
- Copy and Share use the same payload identity. Link operations never fetch media. Media sharing prepares only the selected payload, then opens the platform sheet with a nonempty file, correct MIME and extension, and no credentials in the exported URI or file. Save stays separate.
- Media preparation uses existing authenticated download plumbing, visible cancellable progress, retryable specific errors, and reference-owned temporary files. Files are cleaned after completion/cancellation and startup cleanup removes files older than 24 hours.
- Cancellation, failure, retry, app backgrounding, clipboard limitations, and no compatible share target have visible deterministic outcomes with no unbounded temporary-file growth.
- Source link shows the source website logo; Booru link shows the matching profile icon when configured, with the Booru icon fallback. All other rows have a consistent leading icon.
- Media rows never show a raw URL or “Prepared when selected”. There is no File name row. Original shows already-known dimensions, size, and a file type only when its original URL and post format agree; Image shows those details only when the selected URL is the stored original URL and is absent from all preview fields. Unknown values are omitted without extra metadata requests. Links and Post ID retain their values as subtitles. Action labels and tooltips use i18n fallback; media capability limits remain visible and Video link Copy works wherever text clipboard is available.

## Direct Android image clipboard follow-up (2026-10-04)

Android Image and Original Copy now hands the prepared file to a native clipboard channel. The channel renames that file into `cacheDir/boorusama-clipboard`, publishes its `content://` URI with `ClipData.newUri` through the existing FileProvider, and checks the provider's MIME against the prepared MIME. No bitmap decode, PNG recompression, or second encoded-byte copy occurs. Other platforms continue using their existing image clipboard path. Native Copy leaves at most one clipboard file: a successful new image Copy removes the previous one, and app startup removes orphaned clipboard files while retaining the last successful copy. Share files retain their existing immediate lease cleanup and 24-hour startup cleanup. Clear All Cache or Android cache eviction can remove the retained clipboard file and make a later paste unavailable; this is an accepted cache lifetime boundary. The app does not inspect clipboard contents on focus.
