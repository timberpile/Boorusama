## Follow-up owner decisions — approved 2026-11-15

These decisions supersede earlier optional recommendations and **must be included in the same implementation pass**. No implementation or testing is implied by recording them.

- **Subtree Seen semantics:** In a received Bookmark **combined/subtree listing**, one saved member is **Unseen if it is Unseen in any of the canonical received source Groups represented by the viewed subtree**, including groups exposed additionally as independently subscribed virtual roots. The `All / Unseen / Seen` filter and the 20dp thumbnail marker use this aggregate predicate, consistent with the existing parent Group Unseen badge. On actual full Viewer display **from that combined/subtree listing**, mark this portable member **Seen in every corresponding Group within the represented publisher subtree** (not only the root-first occurrence's chosen Group). Explicit Mark Read of a selected member in that combined view follows the same all-covered-Groups semantics. Individual Group listing/Viewer continues to mark **only that individual Group**. Do **not** broaden marking to unrelated publishers, other source Groups outside this viewed subtree, local copies or another device. Direct child + parent subscriptions refer to the same canonical received Group; no duplicate read-state entries or writes. Continue to require real full-media display, never thumbnail/preload/failed/covered media; never mark read on Group open, navigation/filter changes or notification taps. Capture Group IDs, publisher, source and portable member identities with the displayed occurrence and revalidate current ownership before commit. A source change/Unsubscribe must not allow a stale Viewer callback to mutate another owner.
- **Read-status filter glyph chosen:** **Concept A, a plain outlined Eye icon**, shown before `All`, `Unseen` and `Seen`. Stable icon across choices, localizable accessibility label `Read Status: All / Unseen / Seen`, Title Case for the labels. Other exploratory Eye+dot, funnel and split-disk concepts are rejected for this pass.
- **One global MiteMite Notifications setting:** A single **`Notifications`** on/off toggle on the MiteMite screen controls **all three** native event categories: newly detected devices, newly advertised trusted publications and aggregated newly received Bookmark members. Rename the current user-facing `Device Notifications` label/description appropriately; preserve/migrate the existing stored preference (e.g. `discoveryNotifications`) without resetting it or creating per-device switches. OS permission and channel controls remain independent platform constraints. Do not add per-Group/device notification preferences.
- **Every MiteMite OS notification opens `Bookmarks Home`, not a device, MiteMite subpage, Activity or a particular Group.** Use the real application's Bookmark Home route and avoid duplicate navigation on cold/warm tap. No notification tap acknowledges arrivals or marks a Post Seen. This **replaces** all earlier category-specific destinations.
- **Scope boundaries:** Defer social reactions/cross-device feedback and large multi-device network UX. Primary supported experience is **1–2 connected devices**; preserve existing general identity safety and multi-publisher data semantics (especially batch notification aggregation), but do not spend time optimizing a 5–10-device dashboard or inventing a reactions system.

**Subtree regression scenario:** Group A contains Post P and nested Group B also contains P. A's P is Seen, B's P is Unseen. In A's combined/subtree timeline P displays **Unseen**, is present under the **Unseen** filter, and counts once in the parent badge. Opening P's full media from A's **combined view** marks both A and B Seen, removes P from Unseen, and updates the parent badge; tapping/thumbnail-only/failed full media does not. Opening P from A's **individual Group view** marks A only; B remains Unseen and the parent aggregate still counts P. A separate publisher with the same Post identity stays unchanged. The behavior persists across restart and a direct B subscription virtual link; read-only structure/notification delivery remain unaffected.

## 1. P1: eliminate periodic several-second global UI lockouts

### Report / source evidence

The owner reports **repeated multi-second disabled controls on all MiteMite management pages**, plausibly while syncing. Source inspection supports this causal chain:

- `lib/core/backups/mitemite/providers.dart`: `MiteMiteLifecycle` invokes `service.synchronize()` on startup/resume and from a **30-second polling** timer on Android (plus debounced local mutations and desktop watcher).
- `lib/core/backups/mitemite/service.dart`: `MiteMiteService._run()` sets a single global `busy=true` around serialized actions **including full publish/scan/receive/Activity work and slow SAF I/O**.
- `lib/core/backups/mitemite/page.dart`: a broad range of actions use `service.busy ? null : …`, including editing this device, selecting Storage Location, editing notification preferences, Trust Device, Subscribe/Unsubscribe, Stop Publishing, Forget Device and Retry. The full page rebuilds on ChangeNotifier changes. Merely waiting on background maintenance can therefore disable buttons for seconds.

**Acceptance:** Scrolling, navigation, expanding/copying identity details, opening dialogs, viewing offers, entering alias edits and changing local preferences must remain responsive during ongoing background reconciliation. Avoid “all controls gray every 30 seconds.” A true conflicting destructive operation may need a **targeted** pending state, but should not indiscriminately block unrelated actions or other pages.

**Implementation constraints:**

1. Separate background reconciliation status (`isReconciling`, progress, last result) from **per-operation/target** action state. Do not infer generic UI unavailability from an active poll. Keep `Update Now` truthful; coalesce with a running update rather than launching concurrent operations.
2. Preserve the existing serialized mutation coordinator, source-owned read-only guards, signed publication order, journal atomicity, anti-rollback, retention invariants and safe SAF relocation. Do **not** remove `_run` serialization and `busy` guards indiscriminately.
3. Show interactive dialogs immediately where safe; capture the intended device/source identity, validate at **commit time**, and serialize only the actual data write (queue or await current operation). A queued action must not be silently lost or applied to a different publisher after refresh. Keep explicit progress/error feedback on that action.
4. If some control truly cannot be used during an incompatible operation, restrict that state to **that control** and explain why, without disabling all MiteMite screens. Do not hold whole-page modal barriers across background operations.
5. Distinguish CPU/UI jank (expensive parsing/rebuilds) from disabled state by adding bounded instrumentation or tests; preserve responsive rendering while a slow provider completes.

**Tests:** Use a controllable **5–10+ second deferred SAF/scan future**, open root, Published, Subscriptions and Devices; show navigation/scroll/expand/copy/alias edit/notification toggle responding immediately; queue a targeted Subscribe/Stop Publishing and prove exactly-once correct execution after release; cancel dialog; trust/Forget serialization; prevent two overlapping writes; timer + resume + explicit Update Now coalescing; no receiver-owned edit leak. Verify with Android UI on 320dp and large text.

## 2. P1: three notification categories

### Shared delivery rules

The user **waited several minutes**, considerably longer than the 30-second poll interval, for a new-device alert. Do **not** dismiss this report as normal polling latency. Reproduce on the *actual* current Android install with two independently signed devices and a **fresh** publisher identity. Inspect configured Storage Location, whether two devices use the same directory, enabled global MiteMite **Notifications** preference, `POST_NOTIFICATIONS` runtime grant, Android channel status, app foreground/resume state, `MiteMiteLifecycle` scans, `MiteMiteService.events` pending receipts and `MiteMiteNotifications._schedule` / delivery outcomes. Also test whether a previously seen device's persistent discovery receipt is expected to suppress a new alert.

**Current limitations (source-verified):** `notifications.dart` and `discovery_delivery.dart` deliver **only newly discovered device** events. `SyncDiscoveryDelivery.deliver` currently acknowledges pending discoveries even if the preference is disabled or Android permission is denied (see existing unit test). `SyncEventKind.received` and `SyncLocalEvents` keep Activity information, but there is **no OS-notification implementation** for a trusted device advertising a newly published Group or for added Posts received into existing subscriptions. An ordinary foreground Android poll is not a push service; no notifications are promised while terminated until a permitted later start/resume scan.

**Common architecture required:** a **single durable, typed notification-outbox/delivery coordinator** (or a narrowly compatible extension of local Activity/notification receipts), with separately deduplicated delivery records for **device discovered**, **new published collection available**, and **new posts received**. Store event identity/checkpoints locally, bounded and versioned, without mixing private receiver receipts into shared signed packages or resetting trust. Native OS notifications use the existing app-wide `flutter_local_notifications` initialization/channel handler in `lib/core/downloads/background/notification.dart`; do not initialize a second independent plugin callback or use success toasts. Show only after the relevant authenticated/committed state change, not while preparing a package.

- **Deterministic IDs/tags, durable receipt state and replay-safe delivery:** crash after OS `show` but before receipt commit must not bombard the user; use stable OS tags to update/replace the same event. Failed native display retains retryable intent; denied/disabled preference retains a readable in-app Activity event. Define explicit semantics for whether alerts missed while disabled are delivered after re-enabling, with a bounded freshness policy; **avoid silently erasing pending state before the user can ever receive an enabled notification**. Do not replay months of stale events on permission grant.
- **Privacy:** before explicit trust, notification title/body must contain **no collection labels, media details, filenames, profile IDs or source hierarchies**. Trusted source labels may be shown only after successful authenticated catalog validation. Set Android private lockscreen visibility; support permission denied, channel blocked and settings changes. Keep payload free of secrets/credentials.
- **Navigation — owner-approved:** **Every** MiteMite notification (new device, trusted new publication, aggregated new Posts) opens **Bookmarks Home** using the real app router on cold and warm launches, not a device/group/MiteMite management subpage. Tapping does **not** acknowledge arrivals, mark Posts Seen, or clear the persistent `N` badge. Do not introduce category-specific deep links in this pass.
- **Scope of detection:** foreground startup/resume/periodic scans may discover changes; a notification needs the app to run its scan or be resumed, not an unapproved background worker. Android-native UX and observable latest successful scan/activity should be truthful.

### A. A newly discovered device

A **new identity/fingerprint in the shared location** should trigger one Android notification after verified discovery, including if the publisher has **no published Groups yet**; trust is not required for the generic alert. Fix the current missing-notification report with a real two-device reproduction, not merely the existing mocked notification unit test. Repeated scans/restarts must not duplicate alerts for the same publisher/fingerprint. A changed fingerprint is a distinct security event; **never auto-trust it**. Show a generic `New Device Detected` body until approved.

Test with permission already granted, first-time permission prompt, previously denied + later allowed, disabled/enabled preference, blocked channel, fresh device with no catalog, existing historical device vs truly fresh identity, startup cold tap and resumed warm tap, 2+ consecutive polls and Activity history.

### B. Trusted device publishes a new Group

Detect **new direct publication offers** from a trusted and authenticated publisher by comparing **signed catalog `publicationRoots`** against a durable previously accepted baseline, not every catalog sequence change. Source Group rename, membership-only change, description/metadata edit, same offered root via a different parent/subscription, replay or catalog no-op must not notify. Use publisher UUID + source kind + stable source ID as event key; the authenticated revision/catalog sequence is part of the dedup checkpoint. The first time a device is trusted, establish a baseline from existing offers **without flooding the user with “new Group” notifications**. After baseline, a newly directly published Group should notify even if the recipient has **not yet subscribed** to it. One batch can list multiple new offers concisely. Do not derive new offers from unverified or untrusted catalog content.

**Expected:** `New Collection Available` → **Bookmarks Home**; initial known roots are not reannounced; two roots in one update can be summarized; no untrusted name leak; root advertised through overlapping parents only once.

### C. Subscribed Group receives new Posts

**This is distinct from the persistent Unseen/Seen reading state.** A notification is due when genuinely **new stable Post/member identities** arrive in an already subscribed Bookmark Group after a successful committed incoming revision. Source name/order changes, metadata-only refresh, profile cache/backfill, unchanged revision, retries, viewing an old Unseen Post, and prefetch do not count. **Initial subscription/hydration is a baseline** and must not emit “X new Posts” for all historic saved items. A subscribed Group that gains new children should be handled without counting the same copied member twice. Only actual committed additions count, not advertised but incomplete/invalid packages.

**Owner's important new requirement: ONLY ONE OS notification for new Posts per incoming update/batch, containing ALL new Post changes**, even if the same Group is covered by multiple subscriptions through parent/child overlap and multiple devices or Groups are updated in the same scan. Requirements:

1. **Canonicalize ownership before aggregating.** Multiple root subscriptions, parent/child shortcuts or reimported virtual links pointing to **one canonical source Group** must yield only one member change. Use stable `(publisherId, canonicalSourceGroupId, portableMemberKey)` to identify a membership addition; never notify for one virtual link per subscription.
2. **Deduplicate Post counts across overlapping Groups within a batch.** If Post P is added to both Group A and B, notify **one logical new Post** in the aggregate while retaining the fact that both Groups were affected. Prefer the key `(publisherId, portableMemberKey)` for aggregate per-Post totals across that publisher; maintain all changed Group destinations separately. A different publisher's separate content identity must not be silently conflated. A typed Work/Pool should be counted according to its durable portable saved-member identity, without pretending every Page is a separately received Post.
3. **Coalesce all successful commits during one scan/update into a single pending post-summary event**; use a brief bounded burst-coalescing window if multiple commits finish in rapid succession. Do not show one alert per Group/source/transport file. The single OS notification might say **`7 New Posts` — `Across 3 Groups from 2 Devices`**, with safe, optionally abbreviated trusted Group names in the body. Use one stable OS category/tag and update/merge rather than posting a burst of separate alerts for adjacent scans. Handle a later genuinely new batch normally; do not lose events during delayed, denied or interrupted delivery.
4. **Durable accounting:** calculate from old versus new canonical **committed Group member sets**, not from `unreadMembers`, filtered display counts or a raw sum of `SyncEvent.added`. `SyncActivityRecord` currently stores a per-Group **count** but not a cross-Group portable-member set, so it is insufficient by itself for deduplicated OS totals. Persist sufficient exact identities, a stable batch ID and a delivery cursor/outbox under the same safe source-bound apply/recovery boundary (or an equivalent no-loss journal), and recover missed notification intent after process death without double-alerting.
5. **No false positive or effect on reading:** no alert on first subscribe/initial mirror import; a new Post that is seen in another Group does not erase a genuine new *membership addition* notification. Clicking/clearing a notification **does not mark any content Seen**. Existing per-Group Unseen badges stay independent and update only from Viewer/Mark Read.
6. **Separately handle incoming Source/Following definitions.** This Post summary applies to Bookmark Post/member additions, **not** Following Topic's own feed NEW counters or definition-change dots. Future Following notification design may be separate; do not conflate definitions with newly received media.

**Required examples/tests:**

- Existing parent subscribed; child independently subscribed; one Post added in child → **one OS notification; aggregate count 1**.
- Same Group reachable through 2 or 3 parent/subscription paths → still **one source change** and one alert.
- Post P added to both sibling Groups in one scan → **one alert; Post count 1; both Groups referenced**.
- Groups A/B/C receive 2/3/4 *unique* Posts during one successful scan → **one alert with 9 Posts**, not 3 alerts.
- Different trusted publishers each receive new Posts in the same scan → **one aggregate alert** with correct publisher attribution.
- Initial subscription of 100 existing Posts → **no new-Posts alert**, although persistent Unseen badge may be 100.
- Rename/reorder/post metadata only, failed package then retry, stale catalog, duplicate scan, app restart, parent/source overlap and removal/reappearance → no duplicated already-delivered notification.
- OS notification tapped while offline or after Unsubscribe → **Bookmarks Home**; no crash, resurrection of removed mirrors or automatic Seen/read-state change.
- Bursts on startup/resume and explicit Update Now while scan active → exactly one grouped notification for each genuinely new batch; no UI lockups.
