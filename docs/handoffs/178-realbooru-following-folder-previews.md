## User-visible regression

A Realbooru Following Topic can show up to four fetched post thumbnails in its own overview card, yet its **parent Following Folder** does not show that Topic's thumbnail in its existing four-tile mosaic. This is independent of Realbooru's *unsupported New-Post tracking*: previews work without tracking and must continue to work without making up checkpoints.

### Confirmed source cause

- `lib/core/search/following_topics/src/widgets/following_topic_preview.dart` selects `untrackedTopicPreviewProvider` for unsupported tracking, untrackable ordering or anonymous/public access. Its provider supplies up to **four transient URLs** with a 5-minute successful retention and 30-second negative cache; no new tracked posts or stored `SearchPostPreview` records are created.
- `lib/core/search/following_topics/src/widgets/following_topic_folder_card.dart`: `selectFollowingTopicFolderPreviews` iterates a folder's topic IDs and only includes a Topic if **`topic.previews.firstOrNull` is non-null**. When Realbooru is unsupported, `topic.previews` can be empty while `untrackedTopicPreviewProvider` is populated. The folder therefore omits the Topic **before** `_FollowingFolderPreviewImage` can try to load the transient provider. This is a confirmed code-path mismatch, not a guessed HTTP failure.
- `_FollowingFolderPreviewImage` already reads `untrackedTopicPreviewProvider` for anonymous/public source scopes, but never gets instantiated if no stored preview passed the parent selector. Its present non-public branch assumes every selected candidate has a stored `thumbnailUrl`.
- `lib/core/search/following_topics/src/pages/following_topics_page.dart` builds folder summaries using `selectFollowingTopicFolderPreviews` from recursively collected `searchIds`, topic state and source profiles. Only folder cards currently need this fix; the individual Topic card correctly previews Realbooru.
- `lib/core/search/following_topics/src/providers/untracked_topic_preview_provider.dart` includes the full origin profile/access, query/typed structure, revision and last attempt in `UntrackedTopicPreviewKey`; requests are one first page (`limit: 4`) with `ApiRequestClass.preload`, `dropIfUnavailable`, no cooldown retry, cancelled on disposal and guarded by public access/media visibility. **Reuse this exact provider key and transport.**
- `test/core/search/following_topics/realbooru_preview_production_path_test.dart` demonstrates four decoded URL candidates from one Realbooru search without a stored Topic mutation; the test only renders a Topic, not its parent Folder. `test/core/search/following_topics/search_folder_test.dart` establishes existing **one image per populated Topic, at most four Topics**, ordered by folder membership, no network access for already cached/stored previews.

### Chosen narrow fix — bridge the same preview source into Folder cards

1. Factor the already-deployed Topic preview source decision into a **shared, pure helper** or small provider, instead of duplicating slightly divergent conditions. Inputs: the actual `FollowingTopic`, its **captured** `BooruConfig`, the engine's `searchRefreshQueryAdapter` / `followingTopicTrackingSupportedProvider` and public scope. Return whether it should consume the transient `untrackedTopicPreviewProvider` or stored snapshots. Criteria match `FollowingTopicPreview`, including `SearchRefreshErrorKind.unsupported`, adapter inability to refresh a query, and anonymous/public scope.
2. Make the Folder's **candidate selector** include a Topic with **no stored preview** when a valid source profile exists and the above shared decision says a transient preview is eligible. A candidate should carry stable `topicId`/profile identity and a **nullable** stored URL, not a fake stored `SearchPostPreview`. Do not select candidates lacking a valid profile/source, and do not cross-profile borrow URL lists.
3. Render the four-slot mosaic through a **lazy, profile-aware Consumer widget** with an ordered list of eligible candidates. For a stored candidate, continue using its existing first URL, no additional request. For a transient candidate, watch the exact **same `untrackedTopicPreviewProvider` instance** used by the corresponding Topic card; present the **first eligible URL** from its already validated list, not four URLs from one Topic. This preserves the established one-image-per-Topic contract and cache/coalescing. The parent Folder may start the bounded preview request when visible even if the Topic card is not mounted.
4. Limit live work **to at most four distinct candidate Topics per visible folder at a time**. Resolve the first four **populated** candidates in the folder's established topic order (including eligible transient candidates); avoid unbounded scanning/loading all descendant Topics or starting requests in eager Folder summary projection. While a candidate is pending, reserve only its normal thumbnail slot/placeholder. If it resolves empty or fails, skip it and choose an already-known later stored candidate without firing unlimited new preview requests. No permanent blank slot if another available stored preview can fill it.
5. An anonymous/public-scoped Topic must **not** fall back to a stored thumbnail that might violate its current allowlist. Keep `followingTopicConfigProvider(topicId)` / `anonymousReadScope.isCurrent` and media URL visibility checks authoritative. For regular authenticated Topics, show a stored first URL only when its origin config still matches, and use the transient provider for unsupported-tracking searches even if stored preview data is absent.
6. Do not persist transient results into `FollowingTopic.previews` and do not change `lastSuccessfulCheckAt`, `lastAttemptAt`, unread/new counts, tracking support or refresh scheduling. Do not turn image failures into New-Post tracking errors. Honor automatic media loading disabled, background route inactivity and request cancellation. Keep existing negative caching and error handling; avoid unrestricted HTTP/visibility bypasses.
7. Preserve deterministic layout (four equal square slots, current compact margins) and the existing Folder order/count/search behavior. A folder with one eligible Realbooru Topic normally shows **one** thumbnail, just like a tracked Topic with stored previews. The individual Topic can still show up to four; changing the one-per-Topic mosaic policy is out of scope.

**Implementation seam:** Prefer reusing/adjusting `FollowingTopicFolderPreview` and `selectFollowingTopicFolderPreviews` together with `_FollowingFolderPreviewImage` or extracting a small `FollowingFolderPreviewStrip` consumer. Do not add another source HTTP client, a second cache, a periodic refresh, or a repository migration. If a new pure decision helper is added, use it in both `FollowingTopicPreview` and the Folder to prevent divergent public/unsupported cases. Keep untrusted URL rendering inside the existing `BooruImage` and origin-aware source scope.
