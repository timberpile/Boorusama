# Issue #62 — Bookmark download policy

Branch: `bug/62-bookmark-download-policy`
Base: `6875e0ce778aecfb2b83780c2185ce9273a9b2cc`.

## Implemented portion

The bookmark listing no longer overrides the shared selection download action with the legacy original-only path. Existing shared actions already group resolved posts by originating configuration, validate account identity and invoke the normal DownloadNotifier. The bookmark fallback viewer toolbar also uses that notifier when its source engine repository is available. Quality resolution, engine filename tokens, destination, duplicate handling and resolved-quality sidecars therefore use the ordinary pipeline for those paths. No new download service or policy abstraction was added.

## Important remaining scope

This is **partial**, not a completion claim for #62. `BookmarkLibraryNotifier.downloadBookmarks` remains as the safe stored-snapshot fallback, and `postActionDefinitions` can still choose it for a selection containing missing/ambiguous origins or unsupported bulk engines. Such a mixed selection can therefore still use the legacy policy for otherwise resolvable members. Finish that boundary locally without borrowing the current profile's credentials, fabricating profile identity, silently omitting selected posts or removing the ability to save valid orphaned snapshots. Consider splitting resolved and orphaned targets and reusing common planning at the narrowest existing boundary, rather than rewriting the whole downloader.

Also verify explicit different-quality downloads when a custom filename template produces the same filename: merely reusing normal skip/duplicate behavior is not proof that this acceptance criterion is satisfied. Preserve explicit overwrite/skip choices and avoid accidental duplicate files.
