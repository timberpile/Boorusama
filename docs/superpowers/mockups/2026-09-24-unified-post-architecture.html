Von parallelen Post-Systemen zu einer nativen Post-Pipeline

Dieses Dokument zeigt die Architekturänderungen in feature/bookmark-post-behavior-parity. Es vergleicht die bisherige Trennung zwischen nativen Posts, Bookmarks und Feed-Posts mit dem neuen gemeinsamen Laufzeitmodell, der Snapshot-Speicherung, der profilgenauen Auflösung je Post und dem gemischten Booru-Viewer.

feature/bookmark-post-behavior-parity
Einstiegspunkte4 → 1 Pipeline

Suche, Server-Favoriten, Bookmarks und Feeds laufen nun im selben Laufzeitmodell zusammen.

Post-LaufzeitmodelleViele → Post

Engine-Daten bleiben typisiert, werden aber in einem konkreten Post statt in Unterklassen und reduzierten Kopien zusammengeführt.

Viewer-KontextListenweit → je Seite

Profil, Medienregeln, Details, Overlays und Aktionen folgen dem aktuell sichtbaren Post.

FehlerverhaltenAbsturz/Abweichung → Fallback

Gemeinsame Cache-Daten bleiben mit einer generischen UI, einer Warnung und – wenn möglich – einer Wiederherstellung nutzbar.

Die grundlegende Änderung

Das alte System hatte einen funktionsreichen Pfad für native Live-Ergebnisse und separate, reduzierte Pfade für gespeicherte Inhalte. Im neuen System bleibt die Speicherung getrennt, aber jedes dekodierte Element wird zum selben Laufzeit-Post und durchläuft dieselbe Darstellungs-Pipeline.

Fünf geänderte Architekturschichten

Wähle eine Schicht aus, um ihre Aufgabe hervorzuheben. Jede Schicht besitzt eine klare Grenze: Datenhoheit, Persistenz, Auflösung, Darstellung oder Zustandsisolation.

Neues System
1

Konkreter Laufzeit-Post

PostCoreData besitzt die gemeinsamen Felder. Eine typisierte BooruPostData-Payload besitzt Engine-spezifische Daten. PostOrigin identifiziert die Herkunft des Posts.

Ersetzt die Laufzeithierarchie
2

Versionierte Snapshots

StoredPostSnapshot ist ein Persistenz-DTO und kein weiterer Laufzeit-Post. Engine-Codecs bewahren benutzerdefinierte Daten beim Speichern von Bookmarks und Feeds.

Ersetzt reduzierte Cache-Modelle
3

Engine-Capability-Registry

Jede Engine registriert einen Codec und eine Darstellung. Die Registry prüft die Kompatibilität von Herkunft und Payload, bevor die native UI verwendet werden darf.

Ersetzt zentrale Typannahmen
4

Gemeinsame Karte und gemeinsamer Viewer

PostGridItem und MixedPostDetailsPage rendern jeden Container. Engines liefern Overlays, Toolbar-Teile, Wrapper und Interaktionen.

Ersetzt Container-Viewer
5

Konfigurationskontext je Post

PostPagePresentationScope löst den sichtbaren Post auf und überschreibt schreibgeschützte Konfigurations-Provider lokal. Das appweit ausgewählte Profil bleibt unverändert.

Ersetzt die Abhängigkeit vom globalen Kontext

Klassen- und Verantwortungsübersicht

Dies ist keine reine Eins-zu-eins-Umbenennung. Verantwortungen, die zuvor in Post-Unterklassen oder Container-Seiten gebündelt waren, sind nun auf explizite Modell-, Codec-, Darstellungs- und Kontextverträge verteilt.

Wie ein Post sein natives Verhalten auswählt

Die Auflösung ist bewusst streng. Eine native UI wird erst ausgewählt, wenn sowohl die Profilherkunft als auch die typisierte Engine-Payload kompatibel sind. Jede fehlgeschlagene Prüfung führt zu einer sicheren generischen Darstellung.

Persistenz ist eine Grenze, keine zweite Post-Hierarchie

Bookmarks und Feeds benötigen dauerhafte, JSON-sichere Daten. Suche und Server-Favoriten serialisieren Posts nur dann, wenn eine andere Funktion sie speichert.

Speicherung

Laufzeit

Ein konkreter Post vereinfacht die gemeinsame UI und bewahrt eine typisierte Payload im Besitz der Engine.

Post(
  origin: PostOrigin(...),
  core: PostCoreData(...),
  booruData: DanbooruPostData(...),
)
⇄

Gespeicherter Snapshot

Der Engine-Codec konvertiert nur dauerhafte Werte. Unbekannte neuere Payloads behalten gemeinsame Daten und wechseln sicher zum Fallback.

{
  "origin": { ... },
  "common": { ... },
  "custom": { ... },
  "codecVersion": 1
}
Niemals gespeichert: Zugangsdaten, Provider, Repositories, Callbacks, Controller
Altes Verhalten gespeicherter Postsverlustbehaftete Konvertierung
Reduzierte Bookmark-/Feed-Felder rekonstruierten ein einfacheres Laufzeitobjekt und erfanden Standardwerte. Native Daten konnten durch einen späteren Widget-Wechsel nicht wiederhergestellt werden.
Neues Verhalten gespeicherter Postsversionierte Konvertierung
Gültige Snapshots rendern die native UI ohne Abruf. Alte Bookmarks können über das exakte Profil erneut geladen und als verbesserter Snapshot gespeichert werden, ohne lokale ID oder Gruppenzugehörigkeit zu verändern.

Neue Sicherheitsgrenzen

Der Branch bewahrt nicht nur Felder. Er legt fest, wo Engine-spezifisches Verhalten erlaubt ist und wie Fehler auf einen einzelnen Post begrenzt bleiben.

Korrektheit
◎

Exakte Herkunftsauflösung

Profilhinweise werden nur akzeptiert, wenn Engine und Host weiterhin übereinstimmen. Mehrdeutige Profile autorisieren niemals eine destruktive Aktion.

✓

Payload-Validierung

Die native Darstellung erfordert eine kompatible typisierte Payload. Unbekannte oder fehlerhafte benutzerdefinierte Daten erreichen keine ungeprüften Engine-Widgets.

↔

Begrenzter Provider-Zustand

Jeder aktuelle Post stellt seinen eigenen schreibgeschützten Profilkontext bereit, einschließlich untergeordneter Routen, ohne die globale Auswahl zu verändern.

≡

Sichere Mehrfachaktionen

Profilgebundene Mehrfachaktionen erscheinen nur, wenn jeder ausgewählte Post zur selben exakten, kompatiblen Darstellung gehört.

⌛

Stabile Bookmark-Sitzung

Wird ein Bookmark in seinem Gruppen-Viewer entfernt, erfolgt die Änderung erst beim Schließen der Route. So verschwindet das aktuelle Medium nicht während der Betrachtung.

!

Sanfter Fallback und erneuter Versuch

Fehlende Profile, Engines, Versionen oder Ursprungsposts betreffen nur diese Seite. Gemeinsame Medien und Navigation bleiben verfügbar.

Was sich bewusst nicht geändert hat

Der Umbau ersetzt die Post-Repräsentation und die Darstellungsgrenzen. Die umgebenden Bookmark- und Feed-Funktionen werden nicht neu entworfen.

Umfangsgrenzen
Bookmark-Gruppen

Lokale IDs, Zugehörigkeiten, Konfliktbehandlung, begrenzte Exporte und der Gruppenlebenszyklus bleiben im Besitz des Containers.

Feed-Semantik

Quellenzuordnung, Aktualisierungsmarken, Sortierung, Aufbewahrung, Verlauf, Seitennavigation und NEW-Zustand bleiben unverändert.

Engine-Verantwortung

Engines sind weiterhin für Parsing, Repositories, native Aktionen, Medienentscheidungen und ausschließlich Engine-spezifische Datenverträge verantwortlich.

Offline-Zusage

Gültige gespeicherte Snapshots können statische native UI offline rendern. Serverbasierte Aktionen und automatische Mediendownloads werden nicht offlinefähig gemacht.

Performance im einmaligen Live-Vergleich

Ein Profile-Mode-Lauf mit 1.000 abwechselnden Danbooru- und Gelbooru-v2-Bookmarks zeigte keine praktisch relevante Verzögerung beim ersten Rasterbild. Die reicheren Snapshots benötigen erwartungsgemäß mehr lokalen Speicher.
