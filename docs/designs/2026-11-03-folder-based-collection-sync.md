## 1. Goal, prerequisites, and exclusions

Provide **optional serverless synchronization of selected Bookmark Groups (including nested Groups), Following Topics, and Following folders/feeds** through a user-chosen shared directory. Syncthing or a mounted SMB share may transport the files; Boorusama knows only a directory, not Syncthing, SMB, WebDAV, or a central service.

- Each device independently chooses what it **publishes** and which other devices' collections it **receives**. For example, device A publishes Favorites to B while B publishes different Groups to A.
- Automatic change detection, publication, and verified import work when the app is active and on startup/resume; missed/offline changes are retried. No promise of instant notifications when an app is terminated.
- Received Bookmark Groups **and Following definitions** are source-owned, read-only mirrors: canonical names, memberships/queries, hierarchy and sibling order follow the publisher. The receiver may set **local display aliases for received Bookmark Groups and Following folders (including the owning Feed display)**, without changing those canonical names. Local device aliases, Bookmark arrivals/reading and Following Post refresh/cache/NEW/reading remain receiver-owned. **Create Local Copy** makes independent writable local collections without changing their source subscription.
- Reuse existing `.bsexport` packages and transactional import facilities. No new general export format or direct sharing of Hive databases.

**Dependencies:** [#142](https://github.com/timberpile/Boorusama/issues/142) for retaining valid Bookmarks/Pool references without local profiles; [#143](https://github.com/timberpile/Boorusama/issues/143) for anonymous public-site display and the unavailable-Bookmark counter. [#43](https://github.com/timberpile/Boorusama/issues/43) defines verified alias identities; use the resulting canonicalization rather than duplicate it. Source-level Finding: current manual import profile dependency checks would otherwise block Bookmarks; do not reintroduce that requirement through sync. Following search execution may still require a compatible profile; pause unresolved Following subscriptions safely. The prior unified export/import design listed continuous sync as a non-goal; this is a separate, opt-in consumer of that system, not a change to manual import actions.

**Not in v1:** editing the same mirrored membership on both devices, user accounts/servers, live media transfer, sync of full backups/settings/credentials, cached feed posts/previews, and independent legacy Topic Feed publication.

## 2. Identity, names, folder layout, and content ownership

| Field | Source/receiver contract |
| --- | --- |
| Publisher identity | Random installation ID plus pinned signing public key; never identify by device name alone. |
| Device labels | Publisher chooses an editable display name; receiver initially displays that name but may set a local alias. Neither label is a trust identity. |
| Collection identity | `(publisherId, collectionKind, sourceUuid)` maps persistently to one **local** UUID. Never match by display name. |
| Bookmark Group membership | Mirror portable Post identities and saved snapshots plus typed Pool/Series references; preserve local memberships in other Groups. |
| Received Bookmark Group names | The verified source name is authoritative and still updated on every source rename. A receiver-local **display alias** may override only the name shown in UI; it never edits the canonical mirrored Group or publisher data. Clear alias to show the latest source name. |
| Received Bookmark Group placement/order | The source's parent/child relationships and sibling order are authoritative inside each subscribed subtree. No local move/reorder, cross-device or local-group mixing. Separately subscribed roots appear as independent *virtual entry links* in their device section. |
| Publisher hierarchy | Source Group UUID/parent/position define the canonical tree; scope is the complete present-and-future subtree of each explicitly published root. |
| Received source rename | A publisher's rename updates the stored canonical name after verification without changing Group identity, local alias or post-unread state. If no local alias is set, the UI shows the updated source name; otherwise the alias remains visible until cleared. |
| Received Group hierarchy | Follow source reparenting within subscribed trees. Explicitly subscribed roots remain visible in the device-section root even if they are descendants of another subscribed root; these are navigation links to one canonical Group, not copies. |
| Received Following Topics/folders/feeds | Source owns canonical names, queries, folder hierarchy, sibling order, membership and published Feed definitions. The receiver may set a **local display alias for a received folder**, also used in its Feed header, but cannot rename any source-owned definition, edit queries/feeds, move, reorder, mix with Local or republish mirrors. No received Following Topic alias is added in this scope. Keep compatible local profile binding, auto/manual Post refresh settings, previews/cache, checkpoints and post-NEW/read locally. |
| Credentials, user profiles, private settings, files | Never synchronized. |

A source UUID collision with an existing unrelated local item must create/retain a distinct mapping, not overwrite it. Do not copy the reserved **Default** group over a receiving device's reserved Default: a remotely published Default becomes a regular Group *within that device's received section*. **All Bookmarks is local-only**: it includes records having at least one membership in an ordinary local Group (including local Default) and excludes records that occur exclusively in received mirrors. A Post also present in a local Group remains included exactly once. Device sections do not offer their own All Bookmarks aggregation. Source rename/order/reparent changes must not count as new Posts or reset reading acknowledgements.

**Read-only applies to the entire received Bookmark Group structure**, not just its membership: disable source-name edits, create child, move, reorder, duplicate-in-place, delete, Publish and editing of received Group members/metadata. Receiver-local display aliases are an explicitly permitted separate preference, not Group mutations. Source-owned changes must be applied through the verified sync transaction only. Viewing, in-memory sort/filter/search and viewer navigation are allowed without altering source structure. The user may save a Post from a received Group into an existing **local** Group without changing the mirror. The Bookmark picker and Favorites Sync targets must exclude received Groups; manual imports, bulk actions and All Bookmarks must not mutate them. **Unsubscribe** removes the locally received Group(s), never merely pauses updates. **Create Local Copy** duplicates the selected received subtree into ordinary local writable Groups with fresh local Group UUIDs; the original mirror remains subscribed. Shared saved Post records remain identity-deduplicated; deletion of one mirror must not remove records referenced from other local/received Groups. Guard all of this at the repository/service boundary, not only in widgets. The same boundary applies to received Following definition edits (query, canonical name, feed settings, folder tree, membership/order), while receiver-local folder display aliases and refresh/cached Post/read operations remain writable. Received Following may be **Create Local Copy**-duplicated into independent writable Local Topics/folders/Feeds with fresh IDs; keep its source subscription untouched and never publish the mirror itself.

### Receiver-local collection display aliases — approved 2026-11-15

An explicitly approved exception to **display-name presentation**, not to signed mirror ownership: a receiving installation may set a **local alias for any received Bookmark Group (root or nested) or received Following folder (including its owning Feed header)**. This does not authorize editing canonical source names/records; received Following Topics are **not** aliased under this request. The alias is a receiver-private, durable preference keyed to the canonical `(publisherId, collectionKind, sourceUuid)` identity (or an equivalently stable identity mapping) and not shared across installations. Do not write aliases into signed catalogs, source payloads, published packages, canonical `BookmarkGroup.name`/`TopicFolder.name`, signed definition digests or query/feed definitions. Device aliases remain an independent preference.

Show **Set Alias / Edit Alias** on received Group and Following Folder management menus, with alias removal by clearing and saving the same editor. Empty/cleared aliases restore the *latest* source name. Alias dialogs show the current original/source name for clarity. Render the effective display name consistently on received cards, opened-page titles, navigation/breadcrumbs and the owning Following Feed view, without permanent new badge or metadata rows. Follow existing compact Kurumi layout and localization; selection and ordinary local-group/folder Rename/Edit remain unchanged. A virtual subscription link to the same canonical Group/Folder must use the same alias. Publisher renames, updates, source reorder/reparent, restart, offline periods and overlapping subscriptions leave the local alias intact; deleting the last effective subscription or verified source withdrawal may remove its orphaned alias only after safe confirmed cleanup, and Forget removes only that publisher's aliases. Alias edits create no received-definition change, post NEW/Unseen event, outbound publication, or protocol update. Guard source ownership at the repository boundary, not by relabeling a source rename as an alias.

Implementation stores aliases in private installation preferences (`mitemite.v1.collection_aliases`, local version 1), independently of mirror records. Source-owner checks and alias writes use the existing mutation coordinator; pruning uses recovered committed owner snapshots. Failed persistence retains the last confirmed display value and is retried without granting source edit authority.

See [local-agent implementation task](../handoffs/144-mitemite-received-local-aliases-2026-11-15.md). This decision supersedes earlier statements disallowing **local display-name overrides** but leaves all other read-only and identity contracts unchanged.

## 3. Publishing and overlapping selections

**Publishing a Bookmark Group always publishes everything in that Group**, including its own Bookmark membership, all existing nested Groups and future nested Groups and their contents. The publication scope remains recursive as the Group hierarchy changes. Do not offer a Bookmark Group "Include future children" toggle, exclusions, or a "publish only this Group" mode. A nested Group may additionally be published directly; that direct rule survives stopping its former parent's publication or moving it outside the parent's subtree.

Effective Bookmark Group publication is the union of direct rules and inherited recursive ancestor rules. **One source Group produces exactly one payload/revision history** regardless of overlapping rules. Display `Direct`, `Via Parent`, or `Direct + Via Parent` without extra rows. Source names and paths never define identities. Following Topics/folders remain a separate publication category. Owner decision on 2026-11-14: publishing or subscribing a Following folder/Feed includes all current and future descendant folders and Topics. Keep direct and inherited reasons distinct, preserve one canonical mirror per source definition, and treat a Feed as its owning folder rather than a second source.

**Overlapping publication example:** Publish child Group B directly, then publish its parent A. A and B's other siblings become available without creating a second B, resetting B's revision or changing B's identity. Stop publishing A: B stays published under its direct rule; siblings covered only through A are withdrawn. Stop publishing B while A remains published: B stays available through A. Move a Group out of every published subtree: its publication is withdrawn unless it has a separate direct rule. Moving it within a still-published subtree retains its source identity. Duplicating a source Group gives the copy distinct source Group IDs; within a published parent it is automatically included. Compute the **effective union before emitting the signed catalog**, so a source that remains covered never temporarily appears withdrawn.

Following currently models enabled feeds using Topic folders. The RSS/Feed view's **Publish** action targets that **same** Topic folder/Feed definition, not a second parallel publication. New direct Following publications must target Folders; existing legacy directly published Topics remain available until explicitly stopped in Published. Old Topic Feed codecs remain import compatibility facilities only.

**Stop publishing** commits a signed `withdrawn` state. Once the receiver verifies the publisher, catalog sequence and withdrawal, it removes that collection's received mirror only if no other effective subscription keeps it; deletion must preserve unrelated local memberships, other source collections and transactional recovery. Stopping a direct rule while a parent still publishes the same Group leaves it active. **Deleting** the source emits a distinct signed `deleted` tombstone and removes the receiver mirror **only after** verified authentication and a safe transaction, preserving still-covered descendants, local copies and outside memberships. Missing files, a disconnected directory, lost permissions, or a stale/untrusted catalog must never imply withdrawal or delete local content.

## 4. Receiving and subscription semantics

The Receive view lists discovered devices, including those without publications. Before trust, show only device identity and the trust action; do not reveal collection names, hierarchy, counts, previews or media. After explicit approval, list the device's directly published roots and preserve descendants within their synchronized subtrees. First-time receiving requires explicit publisher approval with separately labeled, copyable device ID and key fingerprint; a device name alone is not authentication. A publisher reinstallation with a new identity/key requires new approval.

Subscribing to a Bookmark Group always subscribes to its **complete recursive subtree**, including all current and future nested Groups, in the source-defined order and hierarchy. There is no destination, local-name, child-exclusion, selective subtree or future-child setting. The new subscription appears as a root entry in that publisher's device section. Source renames/reparenting and new children are reflected automatically after verified updates. The separately approved Following folder/Feed policy also includes current and future descendants; legacy directly published Topics retain their existing single-definition subscriptions, while new publication roots must be Folders.

A Group subscribed directly and included through another subscribed root is **one canonical local mirror** keyed by `(publisherId, kind, sourceUuid)` with one set of members and local reading state. Display every directly subscribed Group as a root entry in its publisher section, regardless of the publisher's parent. **Example:** subscribe B first and its parent A later: both A and B are shown at the device root; B is also navigable in A's source tree, but the two entries point to the *same* B, not duplicate records or separate read checkpoints. Root entries are virtual links, not extra persisted Bookmark Groups. Track direct and inherited subscription reasons separately. Unsubscribing A retains B if it is directly subscribed; unsubscribing B while A remains removes B's independent root entry but not B under A. An inherited-only child has no independent Unsubscribe action. Recompute the effective union *before* committing local deletions or changes in source hierarchy; a verified signed source withdrawal follows section 3, never missing/offline files. When a subscribed ancestor disappears, independently subscribed children remain accessible as device-root entries without losing their stable identities.

Received Following folder sibling uniqueness uses the original `(publisher, source parent)` namespace, including when an unsubscribed parent makes its children appear at Home. Distinct source parents or publishers may therefore expose identically named virtual roots. Preserve their canonical names, source IDs, local UUID mapping and source order across receive, reparenting, unsubscribe and recovery; local writable folder uniqueness remains case-insensitive.

**Unsubscribe** is a destructive local operation: after confirmation, remove the explicitly subscribed root and all its descendants **not covered by another effective subscription**, including their local read-only mirrors and subscription metadata. Remove orphaned Post records only if no other Group retains them; leave unrelated memberships and other subscriptions intact. **Create Local Copy** retains the subscribed source mirror and creates an independent editable local copy with new Group IDs. A verified signed **Stop publishing** follows section 3. **Forget device** is a separate destructive user action: after a confirmation showing the affected collections, remove all mirrors/subscriptions belonging to that publisher and revoke its pinned trust. Leave independently copied Groups, unrelated local Groups/Topics and memberships in other Groups untouched; preserve other local content. Never forget/delete on outage, permission failure or key mismatch. Require new trust approval if the device is discovered again. Never auto-publish a received mirror back to its origin.

## 5. Folder protocol, automatic changes, and safe import

Catalog cycle validation follows only active entries. Withdrawn/deleted entries retain their historical parents and signed revision/retirement authority without adding live hierarchy edges. An active entry may refer to an unpublished/withdrawn parent; that reference grants no implied subscription. Genuine active cycles still fail validation.

Use immutable revision snapshots per **changed** collection, with a separate versioned sync envelope and discovery catalog. One plausible v1 layout:

    v1/
      devices/<publisher-id>/identity.json
      devices/<publisher-id>/catalog/<sequence>.json
      devices/<publisher-id>/collections/<kind>/<source-uuid>/
        <revision>.bsexport
        <revision>.json

There is no migration from the historical `BoorusamaSync/v1` prototype layout: no user publication of this feature has shipped. Start directly with the new versioned layout. Changing an active shared directory is a **transport relocation**, not a new sync identity or legacy-format migration. Validate the new destination before switching; preserve trust, subscriptions, mirrors, local arrival/read/refresh state and publisher revision monotonicity. Safely republish owned active state to the new folder without resetting anti-rollback checkpoints; other devices must point to the new location. Do not delete or publish withdrawal markers to the old folder automatically, and never interpret files missing at either location as a signed deletion.

Private sync authority must survive OS cache eviction without being cloned to a
different Android install. Store the complete `mitemite.v1.*` preference
namespace (identity, settings, trust/high-water marks, reservations, outbox and
receipts) in `noBackupFilesDir/mitemite_private/state_v1.hive` on Android and
app data on desktop. Before key or transport use, migrate the entire existing
cache namespace as one flushed, file/directory-synced snapshot, preserving exact
opaque values. Subsequent serialized per-key writes retain the same durability
barriers. Leave ordinary cache preferences and legacy values in place, but never
read stale legacy authority after a private snapshot exists. Corrupt, partial or
unexpectedly empty existing private authority fails closed; it must not create a
replacement publisher or reset anti-rollback. Existing cache loss before this
upgrade cannot be recovered automatically. This is a local storage migration,
not a shared protocol or source identity change.

The catalog lists source kind/UUID, safe source label, parent source IDs, publication scope, active/withdrawn/deleted state, latest committed revision, and schema capabilities. Revision descriptors include protocol version, publisher identity, source UUID/kind, monotonic revision, package length, SHA-256, schema versions, and a signature. Each device writes **only its own namespace**; no shared mutable group JSON, and two devices never write the same file. No plaintext credentials or full personal export may enter the sync folder.

Capture a consistent scoped `.bsexport` from existing repositories. Persist a dirty signal after completed relevant Bookmark/Following mutations; coalesce bursts with a short debounce. Calculate a deterministic **semantic hash** excluding package timestamps, local Hive keys, Group names, purely local folder placement, read/cached state and other nondeterministic fields. If content is unchanged, skip payload publication; a source-name-only edit updates discovery metadata, not Group content/unread. Perform a full selected-collection reconciliation at startup/resume in case a process died before recording dirty state.

Write a complete immutable payload to temporary storage on the **same destination**, flush, then publish final bytes; publish the signed revision descriptor **last** as a commit marker, and finally the new immutable discovery catalog revision. Ignore temporary paths. Readers check trust, schema, complete byte length/hash, and source identity before applying. On SAF document providers, atomic rename is not guaranteed: unique immutable names plus descriptor-last verification must still be safe. Desktop may use a mounted SMB path, but Boorusama does not implement a native SMB client. Android needs a persisted SAF tree permission/storage adapter rather than turning `content://` into a filesystem path. Avoid excessive directory scans and unbounded archives; keep the latest complete revision plus sufficient historical retention for offline receivers. Delta/event streams are a later optimization only if full changed-collection snapshots prove too expensive.

**Incoming scan:** at app start, resume, while active (watcher plus periodic reconciliation fallback), and via **Sync now**, inspect only subscribed, approved publishers and newer committed revisions. Use existing package validation, preflight, transaction journal/rollback, mutation serialization, stale-revision checks and provider reload. Apply a source revision and persist its last-applied marker **only after successful commit**; retry on errors without partial overwrites. A received import cannot trigger an outgoing publication echo. Keep identity mapping, trust, subscription rules, revision hashes and per-device seen state in app-local versioned metadata, not in the shared Hive boxes.

For Bookmark Group updates, mirror **source-owned membership, names, source-parent relationships, sibling order and typed references**, but not receiver-local read/arrival state, device aliases or unrelated local Groups. Compare stable source/member identities to find new/removed members and apply catalog-only rename/reparent changes without unnecessary payload rewrites. Removing a Group membership never removes a Post that still belongs to another Group; never manufacture unwanted Default membership. Following sync applies publisher-owned definitions (name/query/folder membership/order and Feed configuration) but does not import locally controlled refresh preferences, compatible profile binding, cache, NEW counts, checkpoints or remote Post data. Post refresh is always receiver-owned: its global/per-topic auto-refresh preferences, compatible local profile, request scheduling and rate limits govern network activity; the publisher's auto-update preference cannot override them. If some other mutation path has modified a mirror's membership, show **Conflict** and pause rather than overwriting unexpected local edits. V1 deliberately does not merge simultaneous author edits.

**Version compatibility:** independently check sync protocol, `.bsexport` container version, each source schema and entry types. App version is informative, not the compatibility gate. An older reader can accept newer exports only if all contained source schemas and entry kinds are supported. On unsupported/newer protocol or Bookmark/Following schema, mark only the affected subscription **Update required**, retain last valid content and last-applied revision, and retry after an app update. Never silently drop unknown future types such as newer Pool/Work entries. Distinguish offline, missing source, missing profile for Following, permission revoked, invalid payload, untrusted device and incompatible version. Missing data never means delete.

**Security:** the folder is untrusted input. Pin publisher public keys at approval and verify signed catalogs/descriptors plus payload hashes; reject replayed/suspicious revisions and path traversal, excessive ZIP entries, invalid snapshots and unsafe URLs. Never forward credentials from one host to another or probe arbitrary untrusted endpoints as part of file discovery. Reuse existing trusted import limits and isolate errors by source.

## 7. Unread calculations and acceptance scenarios

**Bookmark Group Unseen count** = `members − readMembers` for the canonical received Group, or the unique union of those Unseen identities across its own publisher subtree. Opening a Group, search/filter changes, sorting and viewport changes never affect the count. Source rename/reorder retains read state; removed members disappear from the count, while a previously Seen identity stays Seen if it reappears. Historical `arrivals`/`hasUnseenChange` fields may remain for journal compatibility and internal activity metadata, but never drive the Group badge, membership dot or Group-open effect. **Bookmark Unseen state, Following Post NEW and Following definition acknowledgements stay independent.**

Required acceptance scenarios:

1. Group A is subscribed on device B under the publisher's device section with **source-owned name and hierarchy**. Source rename/reparent/order/content updates are reflected in canonical mirrored state; receiver-local display alias persists and can be cleared, while source Group rename/move remains unavailable. All new/removed Posts reconcile correctly, including Pool/Series references.
2. Publishing/subscribing to a Bookmark Group includes its present/future subtree. Subscribe child B, then parent A: **both are visible as device root entries** while B also appears within A's source hierarchy, always with one canonical mirror/read state. Unsubscribe one root without disturbing the other effective subscription. No child-exclusion, local placement or future-child switch is offered.
3. No received Groups from separate devices or local Groups may be mixed or moved. A Group independently subscribed and again inherited remains one local mirror; Unsubscribe of a root removes only now-uncovered mirrors, preserving other direct subscriptions. Create Local Copy yields independent editable local Groups and leaves the received source intact.
4. Devices A/B publish **different** collections in opposite directions; offline/resume/repeated import works without duplicate collections or import/export feedback loops.
5. Mirrored memberships, **canonical names, parent/order** and definitions cannot be edited through viewer, menus, selection, Favorites Sync, All Bookmarks or import; a separately stored receiver-local display alias is allowed; view and Create Local Copy work. Local-only All Bookmarks excludes exclusively received records while showing shared identities that are also locally saved. Confirmed Unsubscribe deletes only uncovered received Groups, preserving outside memberships and separately subscribed descendants.
6. Five never-viewed received members display **`5`** before and after Group opening. Display one in the active full Viewer: **`4`**. Mark two selected Unseen members read: **`2`**, retained through reopen/restart. Root/nested aliases share one canonical state; a **normal single-Group** view preserves independent Seen flags in other Groups. In the **combined/subtree** view, a Post remains Unseen while any covered Group has it Unseen; full Viewer display/explicit Mark Read there marks it Seen in **every corresponding covered Group**. Parent aggregates deduplicate identities still Unseen anywhere in their publisher subtree. Test overlapping direct child subscriptions and cross-publisher isolation.
7. Following Home has separate Local and per-publisher device sections. Received Topic/folder/feed canonical names, queries, hierarchy/order and memberships follow the source; received Folders may have receiver-local display aliases, but source editing, moving, mixing or republishing remain rejected by repository/service guards. Source rename/reparent propagates without overwriting local refresh/cache/NEW/read state. Create Local Copy creates independent writable IDs; Post refresh stays receiver-controlled, rate-limited and bound to a compatible profile or current explicit public-access policy. Existing Following post NEW remains unchanged; a separate blue UNSEEN badge can coexist and is acknowledged on successful Topic/search or Folder Feed entry without consuming Post unread.
8. Missing Bookmark profiles reuse #142/#143 and don't lose saved data. Missing Following profiles use bounded public read scopes for explicitly allowed sources; other sources remain paused with an actionable explanation.
9. An older app rejects a newer schema or unknown typed entry **without losing existing content**, records Update required and retries after upgrading; unaffected subscriptions still apply.
10. Untrusted publisher, missing file, half-written file, hash/signature mismatch, duplicate/replay, rollback failure, lost SAF access and disconnected SMB share never silently delete local data. A verified signed withdrawal or explicit Unsubscribe uses the separate safe-deletion contract.
11. Android SAF permissions and provider behavior tested on a device; desktop filesystem; widget tests at compact widths and enlarged text, both navigation shells and normal Group/Feed menu entry points.
12. Explicit Forget device confirms the affected received collection count, removes only that publisher's mirrors and trust, leaves unrelated memberships/independent local copies intact, and requires fresh approval; outages never trigger the action.
13. Received member thumbnails have a compact **top-right** accent-filled Unseen dot with a dark outline; Seen members have none. Hide it during selection so Preview/Zoom remains unobstructed. Show **All / Unseen / Seen** with a **fixed outlined Eye icon (approved option A)** only for mixed read state in the complete unfiltered Group/subtree, or while a non-All filter is active. In a combined/subtree view a member's status is the union of its covered Group memberships. Compose it with search/sort/availability/typed identities, reconcile hidden selection and preserve correct Viewer indices. Local Groups have neither dot nor Seen filter.

14. Receiver-local alias acceptance: assign different aliases to a received Bookmark Group and a received Following folder; show aliases in cards, opened titles and owning Feed; restart and apply a verified source rename/reparent without losing them. Clearing either alias immediately reveals the latest signed source name. A Group exposed as nested and direct root has one alias; different publishers remain isolated. Test alias edit while offline and cleanup only after safe final removal/Forget. ### Receive failure isolation

Reconcile independent subscribed roots of one publisher separately. Old/new
hierarchy overlap, moves and shared saved identities connect roots into one
atomic unit; common unpublished ancestors alone do not. If a newly received
Bookmark reveals shared record metadata in another unit, enlarge the unit before
committing that metadata. Revalidate the current signed catalog and ownership at
every apply. An unavailable/unsupported unit retains its prior data and receipts
while healthy independent units may advance. Project and record successful
partial progress even when the overall update reports a partial failure. Missing
payloads never authorize deletion or a fallback to an older signed catalog.

### Durable local Activity

Commit received definition/membership changes, subscription changes and Local
Copy events in the existing domain journal through a private bounded outbox.
Retain the latest 200 records per domain with monotonic delivery sequences;
consume records and update the history cursor in one local preference value.
A crash after domain commit therefore cannot silently lose or duplicate the
retained Activity. Keep the final history to 200 events in occurrence-time order,
including delayed delivery. Reading, alias edits, cache refresh and private
format upgrades create no source-change events. Operational writes preserve the
outbox; rollback restores it with the corresponding domain data.

Publication history follows a completed signed catalog and its durable local
completion receipt, rather than a selected-but-unpublished intent. Seed legacy
publication receipts without inventing historical events. Delay Forget history
until both domain cleanup journals finish. History delivery/read failures expose
an Activity History Pending state with Retry, preserve committed data and do not
block an independent domain. All outboxes, cursors and completion receipts remain
installation-local and grant no source/trust/write authority.

### Failure history and Storage Location repair

Keep typed, local failure episodes for permission loss, disconnected devices,
missing revisions, unsupported data, identity changes, signature failures,
rollback rejection, conflicts and retryable provider I/O. Repeated polling or
restart does not repeat the same active failure episode; a changed cause or a
new failure after recovery produces a new event. Persist the last attempt and
last fully successful reconciliation separately. Last Updated uses success;
a failed attempt must not replace it. Missing subscribed publishers remain
unavailable with their last valid content intact.

Verify this installation's public identity document even during otherwise
unchanged publication scans. Never overwrite a partial/conflicting identity
file or rotate a signing key. Retry or explicitly choose another Storage
Location, preserving identity, source IDs, trust, subscriptions, journals and
monotonic counters; failed validation of a new folder leaves the current
location unchanged. A failed own publication must not block trusted incoming
work from other publishers.

### Owned immutable-file retention

After serialized publication completes, retain the latest two authenticated,
complete own catalogs (or every complete catalog if fewer exist), every revision
they reference including withdrawal evidence, locally cached complete revisions,
and the newest two reservations per known local collection. Never delete foreign
namespaces, identity files, directories, unknown names, collections without local
reservation evidence, or files above the local high-water mark. Recheck the local
catalog intent, catalog counter and inspected collection counters/caches before
each deletion. A newer staged intent invalidates an older cleanup candidate.

Bound each pass to 128 file deletions and 32 catalog checks, using existing bounded
metadata/payload reads and directory-entry limits. If the catalog-check budget is
exhausted before another complete snapshot is found, discard only confirmed old
incomplete catalogs and preserve all revision files for that pass. Provider I/O
is a retryable maintenance failure, never evidence of obsolete data. An incomplete
newest catalog/payload permits no pruning. Partial historical catalogs become
eligible only after a newer complete signed snapshot supersedes them. Continue
bounded cleanup on later reconciliations; failures preserve current publication
and incoming data and expose Storage Maintenance Pending/Retry. Offline receivers
read the latest complete advertisement without requiring pruned old revisions.
