# Folder-based collection synchronization

Design specification for [#144](https://github.com/timberpile/Boorusama/issues/144). **Specification only; no app implementation has been performed.**

[Interactive HTML reference](mockups/2026-11-03-folder-sync.html) (interactive v5: mobile/desktop device sections, source-owned read-only Groups, full Viewer post reading, conditional selection Mark Read, Publish/Receive and activity). This text is authoritative if the mockup's illustrative data or behavior differs.

## 1. Goal, prerequisites, and exclusions

Provide **optional serverless synchronization of selected Bookmark Groups, Bookmark folders, Following Topics, and Following folders/feeds** through a user-chosen shared directory. Syncthing or a mounted SMB share may transport the files; Boorusama knows only a directory, not Syncthing, SMB, WebDAV, or a central service.

- Each device independently chooses what it **publishes** and which other devices' collections it **receives**. For example, device A publishes Favorites to B while B publishes different Groups to A.
- Automatic change detection, publication, and verified import work when the app is active and on startup/resume; missed/offline changes are retried. No promise of instant notifications when an app is terminated.
- Received Bookmark Groups are **fully source-owned, read-only mirrors**: names, memberships, hierarchy and sibling ordering follow the publisher. The receiver retains only its own new-arrival acknowledgements, reading state and device display alias. **Create Local Copy** explicitly creates a separate editable local Group/subtree without modifying or unsubscribing from the source.
- Reuse existing `.bsexport` packages and transactional import facilities. No new general export format or direct sharing of Hive databases.

**Dependencies:** [#142](https://github.com/timberpile/Boorusama/issues/142) for retaining valid Bookmarks/Pool references without local profiles; [#143](https://github.com/timberpile/Boorusama/issues/143) for anonymous public-site display and the unavailable-Bookmark counter. [#43](https://github.com/timberpile/Boorusama/issues/43) defines verified alias identities; use the resulting canonicalization rather than duplicate it. Source-level Finding: current manual import profile dependency checks would otherwise block Bookmarks; do not reintroduce that requirement through sync. Following search execution may still require a compatible profile; pause unresolved Following subscriptions safely. The prior unified export/import design listed continuous sync as a non-goal; this is a separate, opt-in consumer of that system, not a change to manual import actions.

**Not in v1:** editing the same mirrored membership on both devices, user accounts/servers, live media transfer, sync of full backups/settings/credentials, cached feed posts/previews, and independent legacy Topic Feed publication.

## 2. Identity, names, folder layout, and content ownership

| Field | Source/receiver contract |
| --- | --- |
| Publisher identity | Random installation ID plus pinned signing public key; never identify by device name alone. |
| Device labels | Publisher chooses an editable display name; receiver initially displays that name but may set a local alias. Neither label is a trust identity. |
| Collection identity | `(publisherId, collectionKind, sourceUuid)` maps persistently to one **local** UUID. Never match by display name. |
| Bookmark Group membership | Mirror portable Post identities and saved snapshots plus typed Pool/Series references; preserve local memberships in other Groups. |
| Received Bookmark Group names | Always reflect the source's current name. No local Group rename or name override; only the device section's display alias may be locally edited. |
| Received Bookmark Group placement/order | The source's parent/child relationships and sibling order are authoritative inside each subscribed subtree. No local move/reorder, cross-device or local-group mixing. Separately subscribed roots appear as independent *virtual entry links* in their device section. |
| Publisher hierarchy | Source Group UUID/parent/position define the canonical tree; scope is the complete present-and-future subtree of each explicitly published root. |
| Received source rename | A publisher's rename is reflected at the receiver after a verified catalog update, without changing any Group identity or post-unread state. |
| Received Group hierarchy | Follow source reparenting within subscribed trees. Explicitly subscribed roots remain visible in the device-section root even if they are descendants of another subscribed root; these are navigation links to one canonical Group, not copies. |
| Following Topic/feed | Mirror query, portable site/profile identity, feed/folder configuration; keep previews, caches, checkpoints, post-NEW/unread locally. Locally overridden display names/placement persist. |
| Credentials, user profiles, private settings, files | Never synchronized. |

A source UUID collision with an existing unrelated local item must create/retain a distinct mapping, not overwrite it. Do not copy the reserved **Default** group over a receiving device's reserved Default: a remotely published Default becomes a regular Group *within that device's received section*. **All Bookmarks is local-only**: it includes records having at least one membership in an ordinary local Group (including local Default) and excludes records that occur exclusively in received mirrors. A Post also present in a local Group remains included exactly once. Device sections do not offer their own All Bookmarks aggregation. Source rename/order/reparent changes must not count as new Posts or reset reading acknowledgements.

**Read-only applies to the entire received Group structure**, not just its membership: disable local rename, create child, move, reorder, duplicate-in-place, delete, Publish and editing of received Group members/metadata. Source-owned changes must be applied through the verified sync transaction only. Viewing, in-memory sort/filter/search and viewer navigation are allowed without altering source structure. The user may save a Post from a received Group into an existing **local** Group without changing the mirror. The Bookmark picker and Favorites Sync targets must exclude received Groups; manual imports, bulk actions and All Bookmarks must not mutate them. **Unsubscribe** removes the locally received Group(s), never merely pauses updates. **Create Local Copy** duplicates the selected received subtree into ordinary local writable Groups with fresh local Group UUIDs; the original mirror remains subscribed. Shared saved Post records remain identity-deduplicated; deletion of one mirror must not remove records referenced from other local/received Groups. Guard all of this at the repository/service boundary, not only in widgets.

## 3. Publishing and overlapping selections

**Publishing a Bookmark Group always publishes everything in that Group**, including its own Bookmark membership, all existing nested Groups and future nested Groups and their contents. The publication scope remains recursive as the Group hierarchy changes. Do not offer a Bookmark Group "Include future children" toggle, exclusions, or a "publish only this Group" mode. A nested Group may additionally be published directly; that direct rule survives stopping its former parent's publication or moving it outside the parent's subtree.

Effective Bookmark Group publication is the union of direct rules and inherited recursive ancestor rules. **One source Group produces exactly one payload/revision history** regardless of overlapping rules. Display `Direct`, `Via parent`, or `Direct + via parent` without extra rows. Source names and paths never define identities. Following Topics/folders remain a separate publication category; do not extend this Bookmark-specific simplification to Following definitions without a deliberate product decision.

**Overlapping publication example:** Publish child Group B directly, then publish its parent A. A and B's other siblings become available without creating a second B, resetting B's revision or changing B's identity. Stop publishing A: B stays published under its direct rule; siblings covered only through A are withdrawn. Stop publishing B while A remains published: B stays available through A. Move a Group out of every published subtree: its publication is withdrawn unless it has a separate direct rule. Moving it within a still-published subtree retains its source identity. Duplicating a source Group gives the copy distinct source Group IDs; within a published parent it is automatically included. Compute the **effective union before emitting the signed catalog**, so a source that remains covered never temporarily appears withdrawn.

Following currently models enabled feeds using Topic folders. The RSS/Feed view's **Publish** action targets that **same** Topic folder/Feed definition, not a second parallel publication. Individual Following Topics can also be published directly. Old Topic Feed codecs remain import compatibility facilities only.

**Stop publishing** commits a signed `withdrawn` state. Once the receiver verifies the publisher, catalog sequence and withdrawal, it removes that collection's received mirror only if no other effective subscription keeps it; deletion must preserve unrelated local memberships, other source collections and transactional recovery. Stopping a direct rule while a parent still publishes the same Group leaves it active. **Deleting** the source emits a distinct signed `deleted` tombstone; whether it should trigger exactly the same receiver cleanup remains to be decided. Missing files, a disconnected directory, lost permissions, or a stale/untrusted catalog must never imply withdrawal or delete local content.

## 4. Receiving and subscription semantics

The Receive view lists trusted and untrusted published devices, their source labels, folders, and published Groups/Topics/feeds. First-time receiving requires explicit publisher approval with key fingerprint; a device name alone is not authentication. A publisher reinstallation with a new identity/key requires new approval.

Subscribing to a Bookmark Group always subscribes to its **complete recursive subtree**, including all current and future nested Groups, in the source-defined order and hierarchy. There is no destination, local-name, child-exclusion, selective subtree or future-child setting. The new subscription appears as a root entry in that publisher's device section. Source renames/reparenting and new children are reflected automatically after verified updates. This policy applies to Bookmark Groups; Following Topic/folder subscription policy remains separately specified.

A Group subscribed directly and included through another subscribed root is **one canonical local mirror** keyed by `(publisherId, kind, sourceUuid)` with one set of members and local reading state. Display every directly subscribed Group as a root entry in its publisher section, regardless of the publisher's parent. **Example:** subscribe B first and its parent A later: both A and B are shown at the device root; B is also navigable in A's source tree, but the two entries point to the *same* B, not duplicate records or separate read checkpoints. Root entries are virtual links, not extra persisted Bookmark Groups. Track direct and inherited subscription reasons separately. Unsubscribing A retains B if it is directly subscribed; unsubscribing B while A remains removes B's independent root entry but not B under A. An inherited-only child has no independent Unsubscribe action. Recompute the effective union *before* committing local deletions or changes in source hierarchy; a verified signed source withdrawal follows section 3, never missing/offline files. When a subscribed ancestor disappears, independently subscribed children remain accessible as device-root entries without losing their stable identities.

**Unsubscribe** is a destructive local operation: after confirmation, remove the explicitly subscribed root and all its descendants **not covered by another effective subscription**, including their local read-only mirrors and subscription metadata. Remove orphaned Post records only if no other Group retains them; leave unrelated memberships and other subscriptions intact. **Create Local Copy** retains the subscribed source mirror and creates an independent editable local copy with new Group IDs. A verified signed **Stop publishing** follows section 3. **Forget device** is a separate destructive user action: after a confirmation showing the affected collections, remove all mirrors/subscriptions belonging to that publisher and revoke its pinned trust. Leave independently copied Groups, unrelated local Groups/Topics and memberships in other Groups untouched; preserve other local content. Never forget/delete on outage, permission failure or key mismatch. Require new trust approval if the device is discovered again. Never auto-publish a received mirror back to its origin.

## 5. Folder protocol, automatic changes, and safe import

Use immutable revision snapshots per **changed** collection, with a separate versioned sync envelope and discovery catalog. One plausible v1 layout:

    v1/
      devices/<publisher-id>/identity.json
      devices/<publisher-id>/catalog/<sequence>.json
      devices/<publisher-id>/collections/<kind>/<source-uuid>/
        <revision>.bsexport
        <revision>.json

There is no migration from the historical `BoorusamaSync/v1` prototype layout: no user publication of this feature has shipped. Start directly with the new versioned layout. Moving an already configured and actively publishing shared directory later is a distinct UX/recovery scenario, not legacy-format migration.

The catalog lists source kind/UUID, safe source label, parent source IDs, publication scope, active/withdrawn/deleted state, latest committed revision, and schema capabilities. Revision descriptors include protocol version, publisher identity, source UUID/kind, monotonic revision, package length, SHA-256, schema versions, and a signature. Each device writes **only its own namespace**; no shared mutable group JSON, and two devices never write the same file. No plaintext credentials or full personal export may enter the sync folder.

Capture a consistent scoped `.bsexport` from existing repositories. Persist a dirty signal after completed relevant Bookmark/Following mutations; coalesce bursts with a short debounce. Calculate a deterministic **semantic hash** excluding package timestamps, local Hive keys, Group names, purely local folder placement, read/cached state and other nondeterministic fields. If content is unchanged, skip payload publication; a source-name-only edit updates discovery metadata, not Group content/unread. Perform a full selected-collection reconciliation at startup/resume in case a process died before recording dirty state.

Write a complete immutable payload to temporary storage on the **same destination**, flush, then publish final bytes; publish the signed revision descriptor **last** as a commit marker, and finally the new immutable discovery catalog revision. Ignore temporary paths. Readers check trust, schema, complete byte length/hash, and source identity before applying. On SAF document providers, atomic rename is not guaranteed: unique immutable names plus descriptor-last verification must still be safe. Desktop may use a mounted SMB path, but Boorusama does not implement a native SMB client. Android needs a persisted SAF tree permission/storage adapter rather than turning `content://` into a filesystem path. Avoid excessive directory scans and unbounded archives; keep the latest complete revision plus sufficient historical retention for offline receivers. Delta/event streams are a later optimization only if full changed-collection snapshots prove too expensive.

**Incoming scan:** at app start, resume, while active (watcher plus periodic reconciliation fallback), and via **Sync now**, inspect only subscribed, approved publishers and newer committed revisions. Use existing package validation, preflight, transaction journal/rollback, mutation serialization, stale-revision checks and provider reload. Apply a source revision and persist its last-applied marker **only after successful commit**; retry on errors without partial overwrites. A received import cannot trigger an outgoing publication echo. Keep identity mapping, trust, subscription rules, revision hashes and per-device seen state in app-local versioned metadata, not in the shared Hive boxes.

For Bookmark Group updates, mirror **source-owned membership, names, source-parent relationships, sibling order and typed references**, but not receiver-local read/arrival state, device aliases or unrelated local Groups. Compare stable source/member identities to find new/removed members and apply catalog-only rename/reparent changes without unnecessary payload rewrites. Removing a Group membership never removes a Post that still belongs to another Group; never manufacture unwanted Default membership. Following sync updates definitions/settings but does not import cache, NEW counts, checkpoints or remote post data. If some other mutation path has modified a mirror's membership, show **Conflict** and pause rather than overwriting unexpected local edits. V1 deliberately does not merge simultaneous author edits.

**Version compatibility:** independently check sync protocol, `.bsexport` container version, each source schema and entry types. App version is informative, not the compatibility gate. An older reader can accept newer exports only if all contained source schemas and entry kinds are supported. On unsupported/newer protocol or Bookmark/Following schema, mark only the affected subscription **Update required**, retain last valid content and last-applied revision, and retry after an app update. Never silently drop unknown future types such as newer Pool/Work entries. Distinguish offline, missing source, missing profile for Following, permission revoked, invalid payload, untrusted device and incompatible version. Missing data never means delete.

**Security:** the folder is untrusted input. Pin publisher public keys at approval and verify signed catalogs/descriptors plus payload hashes; reject replayed/suspicious revisions and path traversal, excessive ZIP entries, invalid snapshots and unsafe URLs. Never forward credentials from one host to another or probe arbitrary untrusted endpoints as part of file discovery. Reuse existing trusted import limits and isolate errors by source.

## 6. UI implementation contract

The existing app chrome is mandatory: **mobile Browse / Following / Bookmarks / Menu** (`lib/core/navigation/app_navigation_shell.dart`) and the existing **desktop sidebar**. **Do not create a second bottom navigation bar, new top-level Sync destination, or permanent Sync toolbar.** Bookmark Home displays a local section followed by separate device sections with compact horizontal dividers and sender device names (or device-level local aliases). Device headings and root links are virtual UI presentation, not writable Bookmark Groups. Keep current card geometry, KurumiAppBar, Kurumi menus, navigation/back semantics and `context.t` localization.

### 6.1 Settings and management

Place a **Folder Sync** entry at **Settings → Export & Import**, alongside current Export/Import controls; the current Settings/menu structure is retained. Selecting it pushes a standard settings page (not a new shell). The page contains:

1. One **Shared folder** row with readable, truncated path/document-tree label and **Choose/Change**; show permission errors. Unconfigured state asks for a folder. Sync is disabled until access is valid.
2. Compact **Last sync / status** line with **Sync now**. Show Ready, scanning, offline, blocked, incompatible and failed states without excessive permanent banners.
3. Standard **Publish** and **Receive** navigation rows with relevant counts.
4. A **Sync activity** entry and optional local notification preference.

**Publish page:** reuse the existing Group hierarchy and Following Topics/folders in two compact sections. For Bookmark Groups, a single direct-selection control always publishes the complete present-and-future subtree. Show `Direct`, `Via parent`, or `Direct + via parent` inline; do not expose per-child exclusions, subtree switches, or future-child toggles for Bookmark Groups. A repeated direct+inherited selection yields one published collection. Following folder controls are independently scoped and may retain their own options.

**Receive page:** list discoverable publishers as device cards/list rows, expand their published tree and preview source labels, kinds and revisions. Trust prompt precedes automatic import. Subscribe to a Bookmark Group as one entire-subtree action, with **no local name/destination dialog**; it then appears as an entry at that publisher's device root. Separate subscriptions to an ancestor and child remain distinct root entries, without duplicate mirror data. Subscribed roots show Manage/Unsubscribe with confirmation and the count of mirrors lost after resolving overlapping coverage. Do not offer Unsubscribe on inherited-only children. Disabled/unavailable publisher, empty Group, unsupported schema and missing permissions require distinct compact states. No implicit subscription merely because a file exists.

Collection context-menu actions work even before folder setup: route to Choose folder and return to the intended Publish/Receive action. Multi-selection may provide Publish for selected writable items using the existing selection toolbar.

### 6.2 Bookmark Groups: exact placement

Compare with `lib/core/bookmarks/src/pages/bookmark_group_browser_page.dart` (existing square `_GroupCard`: 2-column mobile grid, thumbnail mosaic, title top-left, overflow top-right, folder glyph bottom-left) and `lib/core/bookmarks/src/widgets/bookmark_appbar.dart` / bookmark list controls.

- On a **received Group card**, show a small **white sync+lock** icon **at bottom-left**, in the indicator corner, with screen-reader meaning "Synced; content read-only". Do not add text or height. An **own published Group card** uses a subdued **upload** glyph in the same corner; no `Published` or `Mirrored` row, label or pill.
- On a **Bookmark folder card**, preserve its existing white bottom-left **folder icon**. When it has publication/subscription status, overlay a miniature upload/sync marker on that glyph rather than create another row. Keep title, preview and menu positions unchanged.
- A **received Group** with unseen incoming additions shows a compact bottom-right numeric badge such as **`+4`**. **No `NEW` text inside this badge**, no update banner or separate Mark as Seen control. If there were only unseen removals/other membership changes, a tiny dot can be used instead. Never overlap selection checkmark or card overflow on narrow screens.
- A **received source parent** may aggregate its descendants' unseen additions (deduplicated by portable member identity). Opening a parent **does not** clear child Group unread counts. Count any repeated root entry/shortcut only once per canonical source Group; a device header may show a deduplicated aggregate.
- **Opening a Group** (card, deep link or Sync activity), after its content is displayed, acknowledges its **new-arrival** `+N`/dot notification only; other Groups retain their notification counts. If the Group is visibly open during a revision, acknowledge it only after rendering that revision. Track reading/viewed state locally per `(publisher, sourceGroup, portablePostIdentity)` so duplicate root/nested links share it; never send it back to the publisher or merge it across different Groups. **Mark an individual Post read only when its content is actually shown in the full Post Viewer**, not from opening its Group, its thumbnail/grid, prefetching or viewing its sibling. Preserve this state across navigation, revisions and restarts. A **Mark Read** multi-selection action is available in received Group post selection **only if at least one selected Post is currently unread**. It marks selected unread Posts read without changing other Groups or the separate `+N` arrival notice. Hide the action for an empty selection or an all-read selection; no separate Group-level mark-read button.
- **Group and folder overflow:** writable local item: **Publish** or **Manage publication** as applicable. Received item: **Create Local Copy**, and **Unsubscribe** only for an explicitly subscribed root; inherited-only children offer no source-mutation or organization actions. Device header offers publisher status, trust and Forget Device. No local rename, move, child creation, reorder or copy-within-received-section actions. Keep menu rows consistent with Kurumi.
- **Opened Group page:** retain existing AppBar and listing controls; place a tiny upload/sync-lock glyph adjacent to the title where appropriate and a normal More action for publication/subscription. **No extra horizontal row** announcing content changes. For unavailable imported Bookmarks, reuse #143's compact blacklisted-post-style count indicator and detailed popup; no duplicate widget.

### 6.3 Following Topics / feed: exact placement

Compare with `lib/core/search/following_topics/src/pages/following_topics_page.dart`, `src/widgets/following_topic_folder_card.dart` and `src/widgets/following_topic_card.dart`: existing title row with folder glyph, feed RSS action, **post NEW**, previews, and metadata/last post. Retain these proportions.

- Small **published upload** or **received sync-lock** icon appears **inline beside existing title/folder glyph**, not in a new status row, not as a large text badge, and not below previews.
- The current Following **NEW** badge and feed post-unread behavior remain **exclusively** for new remote Posts. **Definition changes received from a device** use a visually distinct **small outlined sync icon with a dot** immediately beside the affected Topic/Folder title (or same header slot on Feed view). This must not resemble a post NEW badge or consume a separate row.
- Tapping that sync-change glyph shows a compact description of the definition change and acknowledges **definition changes only**. It must not mark feed posts seen. Do not add change-announcement rows inside Following or an open Feed.
- The **Feed view overflow** exposes **Publish / Manage publication** for its owning Topic folder/Feed. It must refer to the same publication as the Folder card's menu. Respect existing feedEnabled behavior and legacy imports.
- Received Following queries/feed definitions are read-only, but local display name/placement, cache, refresh state and ordinary post unread remain local. A Folder may show both an existing post NEW badge and the separate outlined sync-change glyph simultaneously.

### 6.4 Navigation, activity, responsiveness

- Optionally put a **tiny navigation dot** on Bookmarks when some received Group has unread additions; **do not change** the current four destinations. Following's current nav NEW/dot continues to represent **post updates**, not sync definitions.
- Sync activity shows per-device, per-collection applied additions/removals and definition changes. Opening an affected Bookmark Group from this list clears its seen count through the same Group-open action; opening a definition-change detail acknowledges its separate dot.
- Local device notifications can summarize received updates when permitted; they are not a mandatory instant push mechanism.
- Ensure small widths (320/390 dp), large text, keyboard, pointer/hover, desktop sidebar, selection mode, accessible 48-dp targets and tooltips/semantics. No icons or meaning may depend solely on color; do not mix Material/Kurumi popup row styles.

## 7. Unread calculations and acceptance scenarios

**Bookmark arrival notification count** = newly added stable member identities received since the last successful opening of *that specific* mirror. Accumulate across multiple imported revisions, subtract additions that have since been removed, and don't increment on renamed source labels, snapshot metadata refreshes, cache updates or exports. For unchanged membership but unseen removals, show the small dot until Group open. Unread is not equivalent to the applied-revision marker. Folder aggregates must use unique member identities and not accidentally mark children read. Do not use the literal string `NEW` in a synced Bookmark numeric badge. **Following unread Posts, Bookmark per-Post reading state, Bookmark arrival acknowledgements and Following sync-definition acknowledgements are independent state machines.**

Representative required checks for a later implementation:

1. Group A is subscribed on device B under the publisher's device section with **source-owned name and hierarchy**. Source rename/reparent/order/content updates are reflected; local Group rename/move is unavailable. All new/removed Posts reconcile correctly, including Pool/Series references.
2. Publishing/subscribing to a Bookmark Group includes its present/future subtree. Subscribe child B, then parent A: **both are visible as device root entries** while B also appears within A's source hierarchy, always with one canonical mirror/read state. Unsubscribe one root without disturbing the other effective subscription. No child-exclusion, local placement or future-child switch is offered.
3. No received Groups from separate devices or local Groups may be mixed or moved. A Group independently subscribed and again inherited remains one local mirror; Unsubscribe of a root removes only now-uncovered mirrors, preserving other direct subscriptions. Create Local Copy yields independent editable local Groups and leaves the received source intact.
4. Devices A/B publish **different** collections in opposite directions; offline/resume/repeated import works without duplicate collections or import/export feedback loops.
5. Mirrored memberships, **names, parent/order** and definitions cannot be edited through viewer, menus, selection, Favorites Sync, All Bookmarks or import; view and Create Local Copy work. Local-only All Bookmarks excludes exclusively received records while showing shared identities that are also locally saved. Confirmed Unsubscribe deletes only uncovered received Groups, preserving outside memberships and separately subscribed descendants.
6. Multiple arrivals produce a **numeric-only** `+N` badge; opening a Group acknowledges only its new-arrival notification. Source Group aliases at device root and nested in a parent do not double-count new arrivals or create separate read state. Group opening does not mark Posts read; full Viewer visits and conditional selection Mark Read do. A parent aggregate and non-additive dot behave correctly.
7. Existing Following post NEW is unchanged; a definition-sync dot can coexist on the same folder and is acknowledged without consuming post unread.
8. Missing Bookmark profiles reuse #142/#143 and don't lose saved data. Missing Following profile pauses only its own unsupported subscription.
9. An older app rejects a newer schema or unknown typed entry **without losing existing content**, records Update required and retries after upgrading; unaffected subscriptions still apply.
10. Untrusted publisher, missing file, half-written file, hash/signature mismatch, duplicate/replay, rollback failure, lost SAF access and disconnected SMB share never silently delete local data. A verified signed withdrawal or explicit Unsubscribe uses the separate safe-deletion contract.
11. Android SAF permissions and provider behavior tested on a device; desktop filesystem; widget tests at compact widths and enlarged text, both navigation shells and normal Group/Feed menu entry points.
12. Explicit Forget device confirms the affected received collection count, removes only that publisher's mirrors and trust, leaves unrelated memberships/independent local copies intact, and requires fresh approval; outages never trigger the action.
13. Post reading is per received Group and Post identity: Group opening, thumbnails and preload leave Posts unread; full Viewer display marks just that Post read. A selection of read-only Posts hides Mark Read, while any selection containing unread Posts shows it and updates only those selected unread Posts. A duplicated root/nested navigation link shares one read checkpoint. Incoming `+N` acknowledgements are unaffected by Mark Read.

## 8. Implementation touchpoints and verification

Build on existing infrastructure, not a second state-management stack:

- `lib/core/backups/export_import/export/export_service.dart`, `models/export_selection.dart`, `package/export_package_writer.dart`: selective consistent snapshots.
- `lib/core/backups/export_import/import/import_flow_notifier.dart`, `import_coordinator.dart`, `import_transaction.dart`, `import_preflight.dart`: a reusable *headless, approved-subscription* transactional apply API; avoid widget-bound manual import steps during automatic sync.
- `lib/core/bookmarks/src/providers/bookmark_provider.dart`, Bookmark Group repositories, portable Post/Pool snapshots and shared mutation coordination: detect committed mutations, enforce mirror read-only, update after import.
- `lib/core/search/following_topics/src/providers/following_topics_notifier.dart` and existing Topic folder/feed organization: definitions only, no independent duplicate feed store.
- `lib/foundation/filesystem.dart`: desktop directory operations and suitable Android SAF document-tree adapter with persisted permissions.
- `lib/core/navigation/app_navigation_shell.dart`, existing Group and Following card widgets: reuse current navigation, Kurumi styling and responsive layouts.

The implementation agent must reread `AGENTS.md`, `docs/issue_workflow.md`, the design skill and current code before implementation, use `fvm`, manual Riverpod providers and `context.t`, preserve all existing profile/site security boundaries, and run scope-appropriate tests. This document is the feature contract; any material design changes require reconciliation with #144 rather than silently replacing agreed behavior.
