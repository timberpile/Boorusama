## Independent conclusions and counter-evidence

**C0001:** #113 already recognizes explicit hasMore, but the independently pinned #117 controller still uses nonempty displayed posts as its boundary. #117 session correctly returns explicit continuation after filtering. The common fix is owned here and not yet propagated. No integration/cherry-pick is authorized.

**C0004/C0005:** The first selection tests return `total: 1` on a first page containing one post while expecting a second request. `testPostResult` additionally defaults to `maxPage: 1` and `total: posts.length`; application pagination fixtures inherit those values. These fixtures contradict their own multi-page expectations under the new boundary contract. `_withOrigin` reconstructs PostResult with posts/total/maxPage only and drops hasMore. Fix fixture metadata and preserve explicit continuation; do not weaken assertions or disable real exhaustion.

**C0006:** `jumpToPage` clears retained items, but `_canLoadMore` compares a global result total with only the retained current-page length. Szurubooru and Nozomi provide total without maxPage/hasMore, so a nonempty final later page can leave hasNextPage true. Some page-selector controls can independently bound navigation; that does not establish a correct controller result for all callers. The controller has no explicit request stride, so do not guess it from a short returned page. Check each producer's effective limit/default before choosing a coherent correction. Local regression: page 2 with total 3 and one returned post must be terminal, while a nonterminal filtered page must remain loadable.

**C0007:** Gelbooru `maxPage=(40000-1)~/limit` is the server search-depth cap. `_canLoadMore` returns its comparison before checking a known exhausted total. Thus total=0 with an accessible cap, or reached total below the cap, incorrectly remains loadable. Explicit hasMore must remain authoritative; a known terminal total must not be turned into evidence of more results by an independent upper cap. Test total=0, reached positive total, intermediate total, cap boundary, and explicit override.

**C0009:** A queued debounce survives refresh; an in-flight load-more shares `_page`, errors, loading and pending-completer fields with refresh. Refresh resets the page and replaces results, but the old response/error can append old data, decrement the new page to zero, clear newer pending state or leave the next request skipping page 2. `_fetchPosts` publishes global errors without request identity. Generation checks must cover request, awaited ingestion/filtering and finalizers, not merely network success. Preserve refresh waiter completion and disposal semantics. Use controlled completion signals for old-success/old-error before and after new-refresh completion, scheduled-but-not-started load-more, replacement pending request and dispose.

**C0020:** An initial failed fetch leaves `_page=1`, `_hasMore=true`; RawPostGrid's actionable Load More has no error guard, so fetchMore increments to page 2 without a successful page 1. A later-page error is different and must still retry that later page. Do not use `items.isEmpty` as the sole first-page-success test, because a valid filtered empty cursor page can legitimately advance. Test initial failure/retry, failure after a successfully empty first page, explicit end, and paginated initial-page semantics.

**C0029:** No page-local-total production contract was established in the inspected producers. This does not justify claiming all engines were exhaustively verified. Any future conflicting producer needs concrete source/contract evidence rather than changing the global result meaning speculatively.

**C0031 remains unassessed:** exact Danbooru/Szurubooru pool keys and captured per-page settings require direct source inspection. Also still required before edits: complete relevant helper callers, producer limit defaults, branch/path instructions, fresh ownership and whole proposed diff review.
