## AA01-A01-F0007 — Dynamic mixed-case blacklist entries desynchronize toolbar count and filtering

- **Kind / severity / confidence / lifecycle:** defect / medium / static-confirmed / open.
- **Affected:** #114 T002 and its shared blacklist controller/toolbar.
- **Origin:** inherited case-normalization/state-key mismatch in `PostGridController.setBlacklistedTags`, exposed by the newly required *currently hidden* count and actionable per-rule popup. Not a newly introduced parser or provider bug.
- **Reviewed head/base:** `5bb52794468b172b7d6878fb825b42b00d654675` / `422aeae087c1108e655d85d1a3dac25120456cd6`.
- **Location:** `lib/core/posts/listing/src/widgets/post_grid_controller.dart` lines 147–167, 245–255, 621–635 and 664–680; `lib/core/posts/listing/src/types/active_blacklist_count.dart` lines 3–9.
- **Source:** [dynamic setBlacklistedTags](https://github.com/timberpile/Boorusama/blob/5bb52794468b172b7d6878fb825b42b00d654675/lib/core/posts/listing/src/widgets/post_grid_controller.dart#L147-L167), [visible controls](https://github.com/timberpile/Boorusama/blob/5bb52794468b172b7d6878fb825b42b00d654675/lib/core/posts/listing/src/widgets/post_grid_controller.dart#L245-L255), [filter lookup uses false](https://github.com/timberpile/Boorusama/blob/5bb52794468b172b7d6878fb825b42b00d654675/lib/core/posts/listing/src/widgets/post_grid_controller.dart#L621-L635), [count lookup uses true](https://github.com/timberpile/Boorusama/blob/5bb52794468b172b7d6878fb825b42b00d654675/lib/core/posts/listing/src/types/active_blacklist_count.dart#L3-L9), [expression parser lowercases](https://github.com/timberpile/Boorusama/blob/5bb52794468b172b7d6878fb825b42b00d654675/lib/core/posts/filter/src/tag_expression.dart#L33-L45), [global tag persistence retains input spelling](https://github.com/timberpile/Boorusama/blob/5bb52794468b172b7d6878fb825b42b00d654675/lib/core/blacklists/src/data/hive/tag_repository.dart#L23-L35), [provider passes raw spelling](https://github.com/timberpile/Boorusama/blob/5bb52794468b172b7d6878fb825b42b00d654675/lib/core/blacklists/src/providers/blacklisted_tag_ref_notifier.dart#L45-L75).

### Expected versus observed source behavior

A newly added blacklist rule should immediately hide matching loaded posts, and the unified toolbar should count only actually hidden unique posts and offer the rule's toggle. For an already populated grid with no `cat` rule, a dynamic blacklist change to `{'CAT'}` reaches `setBlacklistedTags`. `TagExpression.parse('CAT')` normalizes to `cat`, so `tagCounts` is keyed by `'cat'`. But `activeFilters` is populated with the raw `'CAT':true` key, not `'cat':true`. Actual filtering uses `activeFilters['cat'] ?? false`, leaving matching posts visible. The newly introduced `countActiveBlacklistPosts` uses `activeRules['cat'] ?? true` instead, incorrectly displaying a positive *hidden* count. `visibleHiddenTags` iterates `activeFilters['CAT']`, sees no `tagCounts['CAT']` and omits its popup toggle.

### Trigger and reachable failure path

An existing grid is loaded; a user adds a mixed/uppercase global or profile blacklist tag `CAT`. The tag repository's `addTag` stores spelling verbatim; `blacklistTagsProvider` yields raw strings; `PostScope` listens for provider changes and calls `setBlacklistedTags`. This can happen without refreshing grid posts. A subsequent page ingest may normalize and add the missing key, masking the bug later, but the immediate loaded view is inconsistent. The static path is fully reachable; UI timing not reproduced.

### Evidence/safeguards checked

Initial data ingest adds unseen normalized `tagCounts` keys to `activeFilters`, so the bug is narrower than all uppercase filters: it chiefly manifests when tags change **after** existing data is loaded. Standard lowercase rules do not trigger the key mismatch. Existing toolbar count tests pass already normalized keys and do not cover this. The old controller already has the mismatch; the new count's default `true` makes the displayed number diverge from actual filtering.

### Root cause and practical impact

Inconsistent canonical representation across parsed rule keys, raw configuration strings, active state map and count fallback leads to incorrect post filtering and misleading popup/indicator state. A previously visible post may remain visible despite adding a rule; the new UI reports it hidden and cannot toggle the problematic rule.

### Minimal recommended correction

Canonicalize rule IDs when building/updating the active filter map (or use the same stable raw rule ID consistently in `tagCounts` and controls), preserve existing enabled/disabled state across normalization, and make hidden count use the **same** active rule semantics as actual filtering instead of contradictory `?? true`. Add widget/controller tests for dynamic uppercase/mixed-case rules after loaded posts, popup toggling and enable-all/disable-all. Do not silently discard unrelated configuration entries.

### Suggested local verification and uncertainty

Execute a controlled provider update and `PostGridConfigurationHeader` widget test (lowercase baseline, then uppercase added after load), plus global/profile blacklist repository/backup tests. No Dart/widget/device test has been run. The source path is verified; prevalence in real user inputs is not.

## AA01-A01-F0009 — Blacklist popup retains an out-of-range chip page

- **Kind / severity / confidence / lifecycle:** defect / medium / static-confirmed / open.
- **Affected:** #114, `feature/114-timeline-toolbar`, T002.
- **Origin:** inherited shared `BlacklistControls` state, newly reused inside the anchored horizontal toolbar popup.
- **Reviewed head/base:** `5bb52794468b172b7d6878fb825b42b00d654675` / `422aeae087c1108e655d85d1a3dac25120456cd6`.
- **Location/source:** [`lib/core/posts/listing/src/widgets/blacklist_controls.dart` lines 14, 83–100, 120–199](https://github.com/timberpile/Boorusama/blob/5bb52794468b172b7d6878fb825b42b00d654675/lib/core/posts/listing/src/widgets/blacklist_controls.dart#L120-L199); [popup controller updates](https://github.com/timberpile/Boorusama/blob/5bb52794468b172b7d6878fb825b42b00d654675/lib/core/posts/listing/src/widgets/post_list_configuration_header.dart#L124-L138).

### Expected versus observed source behavior

The blacklist popup should always offer visible rule chips for a nonempty current rule list. `_currentPageProvider` is a shared `StateProvider<int>` initialized to 1, and `_TagPages.build` uses its value directly for `skip((currentPage - 1) * 30)` with no current-bound adjustment. The page is clamped only by `_setPage` after a pagination-button action. A tag-count or source change does not invoke that setter.

### Trigger and reachable failure path

With >60 matching rules, navigate to page 3. Reduce the list to 31–60 rules (still paginated); `_TagPages` continues skipping 60 and displays zero rule chips despite available entries. The same shared provider can retain page 3 when a different grid/profile opens a popup with 31–60 matches. `PageSelector` receives an invalid page value and user navigation may recover, but the current chips are absent until the state is manually reset.

### Safeguards and alternative explanations

For <=30 tags the widget switches back to nonpaginated `Wrap` and the issue does not arise. If page remains inside the reduced range it is also unaffected. `_setPage` clamps user navigation, but not provider/list changes. These guards narrow rather than disprove the reachable issue. No runtime test or device reproduction performed.

### Root cause and practical impact

The shared pagination state is not scoped to the active tag list and its existing value is not normalized on rebuild. The new popup can appear empty while still claiming active blacklist matches, reducing rule accessibility.

### Minimal correction, checks, and uncertainty

Use a page value clamped to `calculateTotalPage(allTags.length, threshold)` when building, and synchronize/restore provider state at an appropriate lifecycle boundary. Prefer popup- or source-scoped pagination state over a global shared page where feasible without refactoring unrelated controls. Widget-test page 3 -> shrink to 31 matches, popup close/reopen and switching between profiles with differing >30 rule counts. Confirm PageSelector semantics and no setState-during-build errors. Actual device behavior remains untested.
