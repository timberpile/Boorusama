## Implementation assessment

The controller now evaluates explicit `hasMore`, then `maxPage`, then an available `total`, before falling back to raw source-page nonemptiness. The final nonempty page is ingested before stopping. Failed fetch-more requests preserve the current page and remain retryable. Finite `SinglePagePostListScaffold` snapshots explicitly end. Pool ID slicing advertises an end based on the *requested ID slice*, not how many matching/deleted/restricted posts were returned; repository errors are no longer silently converted to successful empty results.

## Investigated limitations and next-cycle probes

- A source without continuation metadata cannot distinguish a genuinely exhausted empty page from a server-side empty intermediary; avoid inventing continuation signals. For known totals, verify per-source semantics before assuming a count is global.
- Refresh while an already scheduled/in-flight `fetchMore` awaits may have legacy race behavior; compare against the pinned base before attributing any issue to #113. Check `_loading`, `_refreshPending` and generation ownership in cycle 2.
- Check that `PostResult.empty()` on an upstream error path does not wrongly denote source completion.
