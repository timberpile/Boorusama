## Implementation assessment

The controller now evaluates explicit `hasMore`, then `maxPage`, then an available `total`, before falling back to raw source-page nonemptiness. The final nonempty page is ingested before stopping. Failed fetch-more requests preserve the current page and remain retryable. Finite `SinglePagePostListScaffold` snapshots explicitly end. Pool ID slicing advertises an end based on the *requested ID slice*, not how many matching/deleted/restricted posts were returned; repository errors are no longer silently converted to successful empty results.

## AA01-A01-F0004 — Existing pagination tests conflict with authoritative totals

- **Kind / severity / confidence / lifecycle:** defect (regression-test failure) / medium / static-confirmed / open.

- **Locations:** unchanged `test/core/posts/post_grid_controller_selection_test.dart` lines 19–58, 61–101; changed `lib/core/posts/listing/src/widgets/post_grid_controller.dart` lines 381–392.
- **Source:** [first legacy test](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/test/core/posts/post_grid_controller_selection_test.dart#L19-L58), [second legacy test](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/test/core/posts/post_grid_controller_selection_test.dart#L61-L101), [new total-aware stop](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/core/posts/listing/src/widgets/post_grid_controller.dart#L381-L392).

### Expected versus observed source behavior

Both existing tests set the first page to one post with `total: 1` and then require fetching page 2 to deliver another post or raise a retryable error. The new controller correctly treats `_items.length=1 >= knownTotal=1` as complete and sets `_hasMore=false`. `fetchMore` returns without making a second request. The first test's `completed == false` assertion becomes false (the returned future completes immediately); the second cannot observe the expected page-2 error or retry. The total supplied by these legacy fixtures contradicts their expected two-page behavior.

### Trigger, safeguards and root cause

This occurs on a simple `refresh()` followed by `fetchMore()`; no unusual timing or live endpoint is required. The newly added #113 tests provide consistent totals, so they do not cover the inconsistent old fixtures. The old tests assume that a reported total can describe only the first page; #113 intentionally trusts valid total metadata. This is a **test-fixture compatibility regression**, not a reason to weaken production pagination.

### Minimal recommended correction

Make both fixtures internally consistent: `total: 2` for the two-page dataset or `total: null` if the total is unknown. Preserve the existing pending-fetch/retry assertions. Add a separate test ensuring a genuine one-post `total: 1` prevents a redundant page-2 request.

## AA01-A01-F0005 — Paginated total-only final page is still reported as continuing

- **Kind / severity / confidence / lifecycle:** defect / medium / static-confirmed / open.
- **Affected:** #113, T001. **Origin:** pre-existing paginated continuation deficiency that #113 did not fix; not newly introduced by the branch's edits, but directly within the advertised pagination scope.
- **Reviewed head/base:** `a1bc1d42903861a46e7230349515946bae678357` / `422aeae087c1108e655d85d1a3dac25120456cd6`.
- **Location:** `lib/core/posts/listing/src/widgets/post_grid_controller.dart` lines 381–392 and 441–461.
- **Source:** [total-only load-more logic](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/core/posts/listing/src/widgets/post_grid_controller.dart#L381-L392), [paginated page reset](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/core/posts/listing/src/widgets/post_grid_controller.dart#L441-L461), [Szurubooru total-only source](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/boorus/szurubooru/posts/providers.dart#L43-L81), [Nozomi total-only source](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/boorus/nozomi/posts/providers.dart#L54-L77).

### Expected versus observed source behavior

In `PageMode.paginated`, navigating to a page calls `_clear()`, leaving only the *current page's posts* in `_items`. For a source that returns `PostResult(total:65, maxPage:null, hasMore:null)` with a page size of 60, page 2 has 5 valid posts but `_items.length=5 < knownTotal=65`. The `total` branch cannot identify the terminal page and falls back to `result.posts.isNotEmpty=true`, so `hasNextPage()` permits a spurious page-3 request.

### Trigger and reachable failure path

Szurubooru and Nozomi post providers return a global `total` without `maxPage` or `hasMore`. Enable paginated mode, navigate to the last nonempty page, and the generic Grid cannot combine the known total with the current page index and page size. The new #113 regression test uses `maxPage:2` and therefore masks this still-open case. This is statically reachable; no device reproduction claimed.

### Root cause and practical impact

The generic count comparison assumes `_items` is an accumulated multi-page list, but `jumpToPage` keeps only the current page. The total alone cannot be compared directly to a one-page post count. Next-page navigation appears available unnecessarily and may fetch an extra empty page.

### Minimal recommended correction

Provide a trustworthy per-page limit or derived last-page bound for total-only repositories, and compare the requested page against the derived global page count without using the locally deduplicated/filtered visible count. Preserve previous-page navigation, source total, and filtered/partial pages. Add a paginated total-only final-page test alongside the existing explicit maxPage test.

### Suggested local checks, assumptions, history

Run focused controller pagination and affected engine consumer tests under FVM, then Android paginated mode with 65 posts at page size 60. Assumes the returned source total means the full result count, as the providers expose. **No local test executed.** Cycle 4 2026-10-29: identified unaddressed inherited defect.

## AA01-A01-F0006 — Gelbooru depth ceiling masks known end-of-results total

- **Kind / severity / confidence / lifecycle:** defect / medium / static-confirmed / open.
- **Affected:** #113, T001; Gelbooru listing consumers.
- **Origin:** the redundant Load More symptom is pre-existing; the newly added `_canLoadMore` metadata precedence is insufficient to fix it for sources where `maxPage` is an accessibility ceiling rather than the last populated page.
- **Reviewed head/base:** `a1bc1d42903861a46e7230349515946bae678357` / `422aeae087c1108e655d85d1a3dac25120456cd6`.
- **Location:** `lib/core/posts/listing/src/widgets/post_grid_controller.dart` lines 381–391; `lib/boorus/gelbooru/posts/providers.dart` lines 43–85.
- **Source:** [new controller precedence](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/core/posts/listing/src/widgets/post_grid_controller.dart#L381-L391), [Gelbooru depth-ceiling source](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/boorus/gelbooru/posts/providers.dart#L43-L85), [Gelbooru API total count parse](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/packages/booru_clients/lib/src/gelbooru/gelbooru_client.dart#L88-L137).

### Expected versus observed source behavior

Gelbooru's `_gelbooruMaxAccessiblePage(limit)` computes the service's hard maximum searchable depth from a fixed cap, *not* the actual result set size. It is returned as `maxPage` alongside the parsed global `count` of matching posts. For example, a search with 5 actual posts and limit 60 can return `PostResult(posts:[5 posts], total:5, maxPage:666)`. After ingesting page 1, `_items.length=5`, but `_canLoadMore` sees `maxPage=666` first and returns `1<666=true`, never checking `total:5`. Thus Load More remains visible even for a known complete result.

### Trigger and reachable failure path

Any Gelbooru search where the known `count` equals already ingested unique source results, but the artificial accessible-depth ceiling is larger than the current page. `hasMore` is absent, so `maxPage` short-circuits completion despite the total. The single-metadata #113 tests test `maxPage` and `total` separately; they miss the conflicting combination. This is source-confirmed conditional behavior, not live Gelbooru reproduction.

### Root cause and practical impact

The new logic treats `page<maxPage` as positive evidence that more data exists, even though this specific source provides `maxPage` only as an *upper bound*. It masks the more informative known total, leaving the original redundant Load More symptom for Gelbooru and potentially other bounded providers.

### Minimal recommended correction

Distinguish maximum reachable page from actual last populated page, or treat a generic `maxPage` as a terminal bound only when `page>=maxPage` and continue checking trustworthy totals/continuation when below the cap. Explicit `hasMore` remains authoritative. Test `maxPage:666,total:5,posts.length:5` and a genuinely incomplete result with an accessibility cap. Account for paginated mode separately as F0005.

Run #113 unit tests with combined metadata and Gelbooru repository adapters, verify actual API count/limit semantics and final-page behavior on an authorized device. No network/device test executed. Cycle 4 2026-10-29: confirmed source contract and wrong priority.

## Cycle 5 — falsification of metadata interpretations and legacy app tests

### F0006 severity/compatibility clarification

The Gelbooru `maxPage` precedence is more than an incomplete optimization: it **regresses the empty-result stop**. `PostRepositoryBuilder.getPosts` supplies the configured `postsPerPage` limit (normally 60), so Gelbooru computes a positive accessible-depth cap. If the API returns **zero** posts (`value.posts=[]`) with a valid `count:0` and the cap is still 666, #113's new `_canLoadMore` returns `_page<maxPage` = true **before checking both the known zero total and the empty source page**. Previously `_hasMore = newItems.posts.isNotEmpty` correctly stopped on the empty page. This creates spurious Load More even for empty search results and potentially repeated requests until the artificial search depth is exhausted. Confirmed by the [new precedence](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/core/posts/listing/src/widgets/post_grid_controller.dart#L381-L391), [depth cap](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/boorus/gelbooru/posts/providers.dart#L43-L85), [result count](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/packages/booru_clients/lib/src/gelbooru/gelbooru_client.dart#L88-L137) and [default limit insertion](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/core/posts/post/src/data/post_repository_builder.dart#L28-L52). **F0006 stays one canonical finding**, medium severity, now explicitly documents a newly worsened path.

The correction must treat a cap as a stopping **ceiling** rather than a guarantee of more pages, and recognize empty pages unless a true source continuation signal explicitly says otherwise. Test `posts:[], total:0, maxPage:666, hasMore:null` in addition to nonempty `total:5` at page 1.

### F0004 further test breadth

[Existing network-recovery application tests](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/test/application/network_recovery_flow_test.dart#L73-L127) explicitly fetch page 2, recover from its failure, fetch page 2 again, and end at an empty page 3. Their `FakeBooruBackend.enqueuePosts` fixtures use the default `maxPage:1`. They are therefore blocked before the page-2 failure/retry can occur under #113, as are the independent pagination-flow tests. Correct helper defaults and all dependent multi-page fixtures together; preserve their meaningful network-recovery assertions.

- Inspected all 16 engine `posts/providers.dart` adapters for reported `PostResult` metadata; most omit total/maxPage (fallback page behavior), some return global totals, and Pixiv/Hybooru return explicit source continuation. This makes metadata semantics heterogeneous across engines.

## Cycle 6 — regression findings independently rederived, without new source assumptions

Replayed the exact relevant source decisions for F0004/F0005/F0006, including `_canLoadMore`'s explicit `hasMore`, then `maxPage`, then `total` priority and the two different Grid storage patterns.

- **F0004:** In the actual source, `refresh()` consumes `PostResult(total:1,maxPage:1,posts:[one])`; `_hasMore=false` immediately, so `fetchMore` exits at its top guard and neither a deferred page-2 callback nor a network-recovery page-2 retry test can run. The failing expectations arise from fixture metadata incompatible with the newly authoritative count, not from the correct stop on a truly complete one-page collection.
- **F0005:** `PageMode.paginated` uses `jumpToPage()` with `_clear` before each successful page. For total-only sources, comparing the *current-page* `_items.length` against a global `total` is mathematically insufficient. The separate `maxPage`-specific unit test demonstrates the intended alternative, but is not a total-only test.
- **F0006:** `GelbooruClientX.getPostResults` always obtains a configured page-size limit through `PostRepositoryBuilder`, so its depth-based `maxPage` is normally present. `_canLoadMore` will treat `page<depthCap` as continued data even when `posts=[]` and `total=0`. This worsens a previously terminating empty-result path. Do not reclassify the cap as a true last-populated-page count.
- Considered counterexamples where source `hasMore=true` despite an empty page: such a response **should** continue because explicit source continuation wins. The minimal Gelbooru fix must not regress that valid Pixiv/Hybooru/slice behavior.

**No additional distinct finding** in this pass. Test status remains inferred statically, not confirmed by an execution. The preferred local fix order is: correct test fixture contracts (F0004), distinguish cap versus actual end for Gelbooru (F0006), then address per-page-count context in total-only paginated mode (F0005), followed by focused and complete regression.
