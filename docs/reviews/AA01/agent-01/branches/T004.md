## Cycle 4 — refresh/fetch-more concurrency and cancellation

- Followed `PixivFavoritesSession.getPosts(1)` through its cancel/reset path against a **currently in-flight** `PostGridController.fetchMore()`. The Grid permits `refresh()` while `_loading` is true, resets `_page=1` before calling the session, and a cancelled prior page-2 fetch can still execute the Grid's `_setPage(_page - 1)` after the refresh reset. The stale error path does not verify that the page/generation still belongs to this fetch. A possible subsequent page 0, stale cancellation error and wrong continuation result are detailed in canonical cross-branch **F0008**.
- The risk is particularly relevant here because refreshing page 1 *actively cancels* the previous session token. `_fetchPosts` reports `RequestCancelledError` from `TaskEither` as a normal Grid error when `_refreshPending` is false; this can also hide the toolbar even after a fresh response.
- Source origin is a **preexisting** generic Grid race, not an intentional new Pixiv failure path. The session's cancellation itself is correct privacy/lifecycle behavior; it should not be removed to hide the Grid defect. #113 changes pagination metadata handling but does not add generation ownership or concurrency guards.
- This race needs controlled-completer tests for delayed page-2 cancellation before/after page-1 completion, result replacement, error cleanup and restored 1-based page. It has not been reproduced on a device.
