## AA01-A01-F0002 — Explicit Pixiv artist previews bypass user media blur

- **Kind / severity / confidence / lifecycle:** defect / high / static-confirmed / open.
- **Affected:** #118, `feature/118-pixiv-following-artists`, T005.
- **Origin:** introduced by the new card surface.
- **Reviewed head/base:** `1d02bef637966999fbd0b72ecb9c6f0e1eedce8a` / `422aeae087c1108e655d85d1a3dac25120456cd6`.
- **Location:** `lib/boorus/pixiv/following/artist_card.dart` lines 17–20 and 44–55.
- **Source:** [new card direct image rendering](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/boorus/pixiv/following/artist_card.dart#L44-L55), [normal Grid covers explicit media](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/core/posts/listing/src/widgets/post_grid_item.dart#L264-L272), [actual blur setting guard](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/core/posts/post/src/widgets/explicit_block_overlay.dart#L49-L111).

### Expected versus observed source behavior

If an account permits R-18 and the user enables `mediaBlurCondition.blurExplicitMedia`, ordinary post thumbnails use `ExplicitContentBlockOverlay(rating: post.rating)` to cover explicit media. New Following Artist previews use only `BooruImage`, with no rating-aware widget or settings check. The account restriction threshold allows known R-18 media when `maxRestriction>=1`, so the card displays its pixels unmasked in this reachable configuration.

### Trigger and reachable failure path

Authenticated Pixiv account with `xRestrict=1` or `2`; user has **Blur Explicit Media** enabled; following feed includes a supplied matching preview with `x_restrict=1`, `visible!=false`, `is_muted!=true`, and a pximg URL. `pixivFollowingPreviewUrls` accepts it by account level; card renders the plain image. No protective overlay applies.

### Evidence and safeguards checked

`BooruImage` implements network/media loading and a global automatic-loading switch, but does not inspect `mediaBlurCondition` or artwork rating. The `ExplicitContentBlockOverlay` is not applied at this new site. This is a static source proof of missing user-configured cover, **not** a device reproduction. URL host and account-level restrictions do not substitute for a user blur preference.

### Root cause and impact

New card view bypasses the normal post-thumbnail rating-specific visibility layer. Explicit previews can appear unexpectedly on the artist list even when the user has enabled the covering preference. This is a material content/privacy regression.

### Minimal correction

Carry a rating/classification alongside the selected DTO preview (rather than only a URL), reuse the existing `ExplicitContentBlockOverlay` or its shared protection pattern for each preview, and keep the source artist card tap/visual dimensions intact. Avoid extra Pixiv requests or a new parallel settings system.

### Local verification and remaining uncertainty

Widget tests with a known R-18 preview under blur on/off and account restriction 0/1/2, tap-to-reveal semantics, narrow cards and state changes; authenticated device verification on a permitted account. Live frequency and whether previews are served for particular accounts is unverified. The branch has no such tests.

## AA01-A01-F0003 — Unknown/mismatched Pixiv explicitness can pass preview threshold

- **Kind / severity / confidence / lifecycle:** risk / medium / high-confidence / open.
- **Affected:** #118, T005.
- **Origin:** introduced by the new preview filter.
- **Reviewed head/base:** `1d02bef637966999fbd0b72ecb9c6f0e1eedce8a` / `422aeae087c1108e655d85d1a3dac25120456cd6`.
- **Location:** `lib/boorus/pixiv/following/presentation.dart` lines 12–22.
- **Source:** [preview threshold](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/boorus/pixiv/following/presentation.dart#L12-L22), [nullable Pixiv fields](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/packages/booru_clients/lib/src/pixiv/types/pixiv_illust_dto.dart#L75-L117), [normal Pixiv rating mapping](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/boorus/pixiv/posts/parser.dart#L256-L274).

### Expected versus observed source behavior

Normal Pixiv post classification treats `x_restrict=1/2` **or** `sanity_level>=6` as explicit, and does not equate missing `x_restrict` with confirmed unrestricted content. The new preview helper instead checks only `(artwork.xRestrict ?? 0) <= maxRestriction` and never uses sanity level. A DTO with missing `x_restrict` or `x_restrict=0, sanity_level=6` passes even for an account `maxRestriction=0`.

### Trigger and reachable failure path

A server-provided preview DTO has a valid pximg URL, matching artist, no `visible=false` or mute flag, but `x_restrict` is absent or contradicts `sanity_level>=6`. The list parser allows nullable metadata; no other check prevents the URL from being emitted. Actual occurrence depends on live Pixiv responses.

### Safeguards checked and impact

The API itself may filter what an account is allowed to retrieve; that server-side enforcement could make the scenario rare. However the new client-side function is less conservative than the existing Pixiv parser, and its own tests check only `x_restrict=1` and visible/artist identity, not missing/mismatched metadata. Treat this as an externally dependent risk, **not** a confirmed live restriction bypass.

### Minimal correction and tests

Share conservative explicitness classification with the existing parser or reject ambiguous/explicit metadata for account-limited previews, rather than defaulting an unknown `x_restrict` to 0. Test null `x_restrict`, high sanity-level, and conflicting values at each account limit. Ensure the separate media-blur preference from F0002 still applies when account permission allows the media.

### History

- 2026-10-29 cycle 1: source-level conditional path found; actual API incidence unverified; open risk.

## AA01-A01-F0011 — Artist-level Pixiv mute flag is discarded before preview selection

- **Kind / severity / confidence / lifecycle:** risk / medium / high-confidence / open.
- **Affected:** #118, `feature/118-pixiv-following-artists`, T005.
- **Origin:** introduced DTO/presentation omission; actual current API behavior for muted artists remains unverified.
- **Reviewed head/base:** `1d02bef637966999fbd0b72ecb9c6f0e1eedce8a` / `422aeae087c1108e655d85d1a3dac25120456cd6`.
- **Location:** [`pixiv_client_following.dart` lines 3–7, 20–35](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/packages/booru_clients/lib/src/pixiv/pixiv_client_following.dart#L3-L35); [`presentation.dart` lines 12–22](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/boorus/pixiv/following/presentation.dart#L12-L22).
- **Contract context:** [Pixiv App API following-user models](https://github.com/akameco/pixiv-app-api#userfollowingid-id-params-pixivparams-promise-pixivusersearch) and [Pixiv API docs](https://pixiv-api.readthedocs.io/en/latest/) describe `user_previews[].is_muted`; [Pixiv Help: Mute](https://www.pixiv.help/hc/en-us/articles/236081388-What-is-the-Mute-feature) explains account mute hides unwanted artworks in listings. These are corroborating external documents, not a captured current authenticated API response.

### Expected versus observed source behavior

When an account is explicitly muted, previews from that account should not unexpectedly show muted artworks merely because it remains followed. The following-user list response has a distinct wrapper-level `is_muted` field in published client schemas. The new `PixivFollowingPage.fromJson` builds `PixivFollowingArtist(user,illusts)` without reading this flag. Its preview selector only checks each `PixivIllustDto.isMuted`, which is an **independent** per-artwork field, and the card renders all accepted URLs.

### Trigger and reachable failure path

A `user_previews` entry includes `is_muted:true` and at least one supplied visible artwork with `illust.is_muted` absent/false, matching artist ID, acceptable rating and CDN URL. Parsing drops the artist-level mute, selects the preview and displays it.
