## Cycle 2 — adversarial concurrency review (2026-10-29T17:50:21.856Z)

### AA01-A02-F0008 — Refresh races with scheduled or in-flight Load More

- **Kind / severity / confidence / lifecycle:** defect / medium / static-confirmed / open.
- **Affected issue/branch/target:** #113, bug/113-collection-pagination, T001. Also relevant for the combined #117 Pixiv list, but this is a pre-existing shared controller race, not a new #113 patch regression.
- **Origin:** pre-existing on develop (confirmed source comparison with 422aeae087c1108e655d85d1a3dac25120456cd6); this cycle inspects the shared modified control path on a1bc1d42903861a46e7230349515946bae678357.
- **Reviewed head/base:** a1bc1d42903861a46e7230349515946bae678357 / 422aeae087c1108e655d85d1a3dac25120456cd6; no stacked branch.
- **Locations:** [refresh and _performRefresh L279-378](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/core/posts/listing/src/widgets/post_grid_controller.dart#L279-L378), [fetchMore L394-438](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/core/posts/listing/src/widgets/post_grid_controller.dart#L394-L438), [F5 refresh L171-175](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/core/posts/listing/src/_internal/raw_post_grid.dart#L171-L175), [mobile pull-to-refresh L285-296](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/core/posts/listing/src/_internal/raw_post_grid.dart#L285-L296).

#### Expected versus observed source behavior

Refresh should replace the current list atomically and prevent an older next-page task from changing its page index or publishing stale results. The controller uses a delayed debounce timer for fetchMore but refresh neither cancels this timer nor checks the _pendingFetchMore/_loading work. FetchMore does not reject calls during _refreshing and has no generation/snapshot guard after awaiting source data.

#### Trigger and reachable failure path

Starting from a loaded infinite page 1, schedule fetchMore(page 2), then initiate a keyboard F5 or pull-to-refresh before or during its request. Refresh sets _page=1 and starts a fresh page-1 fetch; the pending Load More timer can then set _page=2 and fetch page 2. If page 2 resolves before refreshed page 1, it is ingested, then refresh calls _clear and replaces data with page 1 while _page remains 2. The next Load More increments to page 3 and skips all page-2 items. If the response ordering reverses, stale old-context data can instead be ingested after refresh, depending on source query.

#### Evidence and safeguards checked

Current _refreshPending coalesces multiple refreshes, not Load More. _pendingFetchMore coalesces multiple Load More tasks only. UI _onControllerChange avoids rendering intermediate refresh state but does not cancel the timer/fetch. The same missing interlock is present at the develop base, thus this is not introduced by #113. [Existing refresh tests](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/test/core/posts/listing/post_grid_controller_refresh_test.dart) cover overlapping refresh, and [exhaustion tests](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/test/core/posts/listing/post_grid_controller_exhaustion_test.dart) cover sequential paging, not the two concurrent operations. No backend guard is visible in the generic controller.

#### Root cause and practical impact

Independent refresh and Load More mutations lack a shared request-generation invariant. Infinite lists may lose an entire page, mix old/new query results, or leave _page inconsistent with the loaded content.

#### Minimal recommended correction

Make refresh invalidate pending Load More generations and cancel the unsent timer; ensure any existing deferred fetchMore completer completes. Guard in-flight Load More results and page/index writes against a changed refresh generation, and suppress new Load More while refreshing. Prefer one narrow shared-generation invariant rather than a larger controller rewrite. Preserve retry and disposal behavior.

#### Suggested local verification and regression checks

Add deterministic Completer-gated controller tests for both completion orders, refresh during debounce, changing source query while page2 is pending, page index after cancellation, and dispose/Load More completion. Re-run #113 exhaustion and refresh suites and #117 filtered cursor cases after integration; verify F5 and pull-to-refresh on Android.

#### Assumptions and remaining uncertainty

This is a source-demonstrable race with manually controlled asynchronous completions; occurrence probability and affected real endpoints are unmeasured. No Flutter runtime test was executed. The current finding does not allege #113 introduced the concurrency bug.

## Cycle 4 — Gelbooru metadata contract versus exhaustion precedence (2026-10-29T18:12:37.448Z)

### AA01-A02-F0011 — Gelbooru capacity maxPage outranks completed result count

- **Kind / severity / confidence / lifecycle:** defect / medium / static-confirmed / open.
- **Affected issue, branch, target:** #113, bug/113-collection-pagination, T001. **Origin:** pre-existing end-detection symptom; the new #113 metadata precedence leaves a concrete acceptance requirement unfulfilled, not a new regression compared to develop.
- **Reviewed head/base:** a1bc1d42903861a46e7230349515946bae678357 / 422aeae087c1108e655d85d1a3dac25120456cd6. No stacked implementation branch.
- **Locations:** [Controller _canLoadMore L381–392](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/core/posts/listing/src/widgets/post_grid_controller.dart#L381-L392); [Gelbooru response adapter L43–84](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/boorus/gelbooru/posts/providers.dart#L43-L84); [Gelbooru API count parsing L114–137](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/packages/booru_clients/lib/src/gelbooru/gelbooru_client.dart#L114-L137); [controller tests L11–30](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/test/core/posts/listing/post_grid_controller_exhaustion_test.dart#L11-L30).

#### Expected versus observed source behavior

Issue #113 requires complete collections to omit redundant Load More when trustworthy counts establish exhaustion. Gelbooru getPostResults returns total=value.count (the response's global result count) and maxPage=_gelbooruMaxAccessiblePage(limit), which is a technical upper bound (39999~/limit) rather than the number of matching pages. For limit=20 and count=5, the complete first response has 5 posts, total=5, maxPage=1999, hasMore=null. The #113 controller checks _page<maxPage first, returning true and skipping the later _items.length>=total termination check. The user sees unnecessary Load More even though all five results were loaded.

#### Trigger and reachable failure path

Open a Gelbooru search with five matching posts and postsPerPage=20. Refresh receives full five items, global total=5 and search cap maxPage=1999. _page=1, so _canLoadMore returns true. Tapping Load More fetches an empty second page and still returns true while _page<1999; the redundant control may persist indefinitely until a cap is hit, despite complete results. Exact remote Gelbooru API fixtures were not run, but this conditional flow is statically established from the concrete adapter and controller.

#### Evidence and safeguards checked

The client parses count from response @attributes.count; the adapter maps it directly into PostResult.total without converting maxPage to actual count-derived pages. _items holds unfiltered accepted posts, so the five-post example meets the count stop condition if the code reaches it. Other #113 tests assert a total-only case and a maxPage-only case separately; none supplies both total=5 and maxPage≫1 as Gelbooru does. The new explicit hasMore precedence is correct for cursor sources but Gelbooru does not set it. This misclassification already existed on develop under nonempty-page fallback, but was not fixed by #113.

#### Root cause and practical impact

A metadata field named maxPage is used for a search-capability upper bound by one engine yet treated as proof that additional result pages exist. When actual count contradicts the cap, capacity takes precedence over known completion and causes redundant repeated requests.

#### Minimal recommended correction

Treat trusted total completion as terminal even if maxPage describes an upper search bound. Where both metadata fields are present, both exhaustion constraints should bound continuation: explicit hasMore first when authoritative, then known reached total, then reached maxPage. Preserve the no-metadata fallback for sources without trustworthy information, and avoid suppressing genuinely incomplete filtered or duplicated pages.

#### Suggested local verification and regression checks

Add a deterministic controller test returning posts=[5 valid test posts], total=5, maxPage=1999, hasMore=null at page1: expect hasMore=false and no second fetch. Cover total larger than first page while maxPage is high, exact total reached on page2, total=0 empty result, and explicit hasMore override. Run actual Gelbooru small-search pagination and check no redundant Load More, then run #113 and final-grid regression on FVM/Android.

#### Assumptions and remaining uncertainty

The example assumes the API's @attributes.count is the search-wide count as used by its current adapter. All five returned posts have parseable media and unique IDs; malformed/filtered remote records are a separate metadata contract. Static confirmation is conditional on the stated response shape, not a live repro. The behavior predated the patch and is an acceptance gap, not a newly introduced regression.
