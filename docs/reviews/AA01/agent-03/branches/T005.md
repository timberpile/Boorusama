### AA01-A03-F0003 — Following artist artwork previews bypass configured explicit-media cover

- **Kind / severity / confidence / lifecycle:** defect / **high** / **static-confirmed** / open
- **Affected:** #118, `feature/118-pixiv-following-artists` (T005). **Origin:** introduced new standalone artwork preview surface without the existing explicit-content guard.
- **Reviewed head / base:** `1d02bef637966999fbd0b72ecb9c6f0e1eedce8a` / `422aeae087c1108e655d85d1a3dac25120456cd6`.
- **Exact source:** [following artist card 19–21, 44–55](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/boorus/pixiv/following/artist_card.dart#L19-L55); [preview filter 12–22](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/boorus/pixiv/following/presentation.dart#L12-L22); [account maxRestriction 22–34 and callsite 102–106](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/boorus/pixiv/following/page.dart#L22-L34); unchanged [image widget 77–119](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/core/images/booru_image.dart#L77-L119); normal [PostGridItem 264–273](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/core/posts/listing/src/widgets/post_grid_item.dart#L264-L273) and [ExplicitContentBlockOverlay 49–113](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/core/posts/post/src/widgets/explicit_block_overlay.dart#L49-L113).

#### Expected versus observed source behavior

With the user's **Blur explicit media** listing preference enabled, explicit artwork previews should be covered until deliberately revealed, as normal post-grid thumbnails are. The new card renders accepted Pixiv URLs directly through `BooruImage`. That widget does not implement rating-based covers; `ExplicitContentBlockOverlay` only wraps normal `PostGridItem` in the existing listing path, not the new artist card.

#### Trigger and reachable failure path

For a Pixiv profile whose account metadata permits R-18 (`xRestrict >= 1`), the presentation helper allows previews with artwork `x_restrict=1` and uses the account capability as its sole explicitness threshold. With `mediaBlurCondition=explicitOnly`, the accepted preview gets an ordinary unmasked `BooruImage` and becomes visible. This is source-reachable independent of extra API calls. The Pixiv parser's separate `pixivRatingFrom` also classifies `sanity_level>=6` as explicit, which this preview path does not consider.

#### Evidence and safeguards checked

The preview helper correctly rejects `visible=false`, `is_muted=true`, foreign artist IDs and URLs outside HTTPS pximg.net, and restricts artwork to the account's content level. Those server/account guards are not equivalent to the local **explicit-media-cover user preference**. `BooruImage` supports automatic-media-loading blocks but contains no rating/blur handling. The presentation tests exercise server-level restriction only; no media-blur widget test exists for this new card.

#### Root cause and practical impact

A new media surface bypasses the established app-level explicit-content presentation layer, making potentially sensitive images visible despite the user's explicit concealment preference. This affects the Following Artists preview strip of authorized adult Pixiv accounts; no claim is made about content being downloaded when the global automatic-media loading option is disabled.

#### Minimal recommended correction

Apply the existing `ExplicitContentBlockOverlay` per Pixiv preview, deriving the rating through the established Pixiv rating parser (`x_restrict` and `sanity_level`) and preserving the existing user-reveal interaction. Continue to avoid per-preview API calls.

#### Suggested local verification and regression checks

Widget-test adult-account `x_restrict=1`, unknown `x_restrict` plus `sanity_level=6`, explicitOnly on/off, reveal action, multiple previews, plus existing visibility/URL checks. Verify on Android in the Following Artists page with configured media blur and screen recording/screenshot handling that does not reveal private payloads.

#### Assumptions and remaining uncertainty

The finding is source-confirmed as a missing established presentation guard, **not** reproduced on a device. Actual frequency depends on account permissions and supplied artwork.

### AA01-A03-F0004 — Following preview visibility ignores app-level tag blacklist rules

- **Kind / severity / confidence / lifecycle:** risk / **medium** / **high-confidence** / open
- **Affected:** #118 T005; **origin:** introduced new read-only preview surface without an app-level blacklist integration.
- **Head / base:** `1d02bef637966999fbd0b72ecb9c6f0e1eedce8a` / `422aeae087c1108e655d85d1a3dac25120456cd6`.
- **Source:** [presentation helper 12–22](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/boorus/pixiv/following/presentation.dart#L12-L22), [card 18–55](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/boorus/pixiv/following/artist_card.dart#L18-L55), [PostScope and its blacklist provider 65–94](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/core/posts/listing/src/widgets/post_scope.dart#L65-L94).

#### Expected versus observed source behavior

Normal post timelines apply active local tag blacklist rules through the post controller. The new preview helper only checks server visibility, muted state, artwork ownership, account restriction and URL host. It does not inspect Pixiv artwork tags or the user's local blacklist; nor does the artist card subscribe to any blacklist provider.

#### Trigger and reachable failure path

For a supplied artist preview whose tags match a user-configured blacklist, the new card can still present the artwork. This is source-evident, but **whether the product intentionally applies full post-blacklist policy to an artist-card strip** needs confirmation: the issue asks for previews and the author's handoff explicitly defers this content-rule acceptance check. Do not count this as a statically proven contract violation without that decision.

#### Evidence and safeguards checked

Account-level restrictions, foreign-user exclusion, muted/hidden checks and URL allowlisting were verified. None consumes or evaluates a local tag blacklist. No pre-existing post controller is used on this page. No extra per-artwork requests should be introduced as a correction.

#### Root cause and practical impact

The preview implementation has no application-level blacklist adapter and can display art a user meant to suppress. Tags may be absent or incomplete in provided preview DTOs; do not assume complete server data.

#### Minimal recommended correction

Confirm product policy for new artwork preview surfaces; if blacklist parity is required, reuse existing local rule matching against any server-supplied tags before rendering (or fail closed for insufficient data as the agreed UX requires). Preserve server-call budget and avoid new per-card requests.

#### Suggested local verification and regression checks

Provide an artist with a supplied preview containing an explicitly locally blacklisted tag; exercise current profile/global filter rules, unrelated artist art, and no-tag DTOs. Test alongside the explicit-media cover case. Ensure cards still open artist search and pagination remains intact.

#### Assumptions and remaining uncertainty

Static lack of blacklist integration is clear; expected UX for this new summary surface and completeness of server-supplied tags remain open. Severity applies if preview parity is required.
