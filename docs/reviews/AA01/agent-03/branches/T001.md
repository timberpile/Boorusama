#### Expected versus observed source behavior

After page 1 fails, the controller should expose the error and retry page 1, not allow fetching page 2 first. The changed `_canLoadMore` returns `true` whenever `errors.value != null`. On the initial failed refresh, `_fetchPosts(1)` sets the error and substitutes an empty result. `_performRefresh` then sets `_hasMore=true`. Unlike the develop baseline's `newItems.posts.isNotEmpty` (false on error), the new branch exposes the Load More affordance while still on an unsuccessful first page.

#### Trigger and reachable failure path

A network failure (or malformed data mapped to a left result) during first-page refresh sets `errors`. With a short error sliver, `RawPostGrid` shows a Load More button at the bottom because its `hasMore` flag is true. Pressing it calls `fetchMore`, increments the controller page from 1 to 2 *before* requesting. `_fetchPosts(2)` clears the page-one error, so successful page 2 results are displayed without page 1. This affects infinite mode and can also pollute page-mode next-button availability.

#### Evidence and safeguards checked

The changed tests cover a **failed later page** that retains the previous valid page and retries the same page number; they do not cover the failed *initial* page, whose controller state differs. The `fetchMore` failure rollback is appropriate for later-page failures and can be kept. Error surfaces allow refresh retries for supported error types; that does not prevent a simultaneously rendered Load More action.

#### Root cause and practical impact

Retryability of a later-page load was conflated with source continuation after a failed initial refresh. Users can skip the first page under ordinary network/API failures and see an incomplete grid until a full refresh.

#### Minimal recommended correction

On an initial failed refresh or failed paginated page jump, avoid marking a *new* page as loadable merely because an error occurred. Keep the existing valid continuation state for failed page 2+ requests (which already roll back the page) and use explicit same-page refresh/retry for page 1. Preserve the metadata-driven completion behavior for successful responses.

#### Suggested local verification and regression checks

Add a regression test: page 1 fails once; controller.page remains 1, `hasMore` does not advertise the next source page, subsequent refresh retries page 1 and then page 2 can load. Also test page 2 fails and is retried on page 2, plus paginated-mode page failures and an actual short error UI on Android. Run FVM test and full final candidate regression.

#### Assumptions and remaining uncertainty

The state and UI path are directly inspected and static-confirmed, but the exact rendered button position on a given device was not tested; viewport-dependent layout may alter the displayed action.
