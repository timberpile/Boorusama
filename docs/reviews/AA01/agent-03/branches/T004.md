#### Expected versus observed source behavior

Renaming the current Pixiv profile (or changing its listing-only preference) must not break Favorites refresh/pagination. Such edits change `BooruConfig ==` but leave `config.auth` and `config.id` unchanged. The `Provider.autoDispose.family` is keyed by the **whole** new `BooruConfig`, so `_FavoritesView` watches a new session and releases the old auto-disposed provider. However both `_FavoritesView` and nested `PostScope` retain their previous widget keys: `PostScope.initState` created its `late final PostGridController` with **the old session's `getPosts` method**, with no `didUpdateWidget` to replace the fetcher.

#### Trigger and reachable failure path

Open Pixiv Favorites, then update the same profile's name or profile-only listing settings through the existing config notifier while retaining its account credentials. `ref.watchConfig` observes the changed config, the new provider family member is read, and the old member is disposed, invoking `PixivFavoritesSession.dispose`. The surviving PostGridController's existing fetcher then points to `_disposed=true` session; its `_fetch` throws a canceled error before requesting the next page. Load More, refresh and recovery are disabled until the view is recreated. This is source-reachable; exact UI timing and device reproduction remain unverified.

#### Evidence and safeguards checked

The auth key **does** contain `passHash` and token credentials, so account changes normally recreate `PostScope` and avoid this mismatch. That safeguard does not cover ordinary non-auth profile changes. `PostScope` owns the fetcher for its full mounted lifetime and does not follow widget.fetcher changes. The new #117 tests isolate sessions and do not exercise a live config-only update through this UI.

#### Root cause and practical impact

Provider identity and controller identity disagree. A harmless profile edit prematurely disposes the session that the live grid continues to use; data already displayed may remain while browsing future pages is impossible. No evidence of data leakage across different credentials in this path.

#### Minimal recommended correction

Keep session provider identity aligned with the source scope used by `PostScope`: derive the family key from stable account/visibility/origin identity instead of the entire mutable `BooruConfig`, or key `PostScope` by the actual session identity and recreate it when the provider changes. Prefer the former to preserve loaded pages and avoid unnecessary network resets on cosmetic edits. Keep account token changes isolated.

#### Suggested local verification and regression checks

Widget/provider integration: open Pixiv Favorites with several pages, update only profile display name then listing preferences while Favorites stays mounted; assert no unnecessary session disposal or page-one refetch; load subsequent pages, refresh, switch Public/Private and then change login/account, verifying old private results are never reused. Run with FVM and Android.

#### Assumptions and remaining uncertainty

A config update must reach the watched `currentReadOnlyBooruConfigProvider`; the code permits it and listens to changes. No runtime reproduction has been executed. Riverpod autoDispose's exact frame timing does not affect the eventual dangling fetcher.
