#### Expected versus observed source behavior

#117 promises cursor pagination preserving valid next-page links even if the current page's content is filtered, restricted, or empty. The session deliberately returns `PostResult(posts: [], hasMore: true)` when filtered artwork yields no Posts but a server cursor remains. However its actual `PostGrid` uses the pinned pre-#113 controller, which sets `_hasMore = newItems.posts.isNotEmpty` on both refresh and fetchMore, discarding `PostResult.hasMore` entirely. Thus the UI stops after the empty first/intermediate page despite a valid continuation.

#### Trigger and reachable failure path

The #117 test constructs a first page with one invisible artwork and `nextBookmarkId: '90'`, resulting in **zero visible Posts but `hasMore: true`**, followed by a nonempty second page. The unit test calls `session.getPosts(2)` directly, so it passes. In the real page, `PostScope<Post>` wires `session.getPosts` into `PostGridController`. A refresh sets `_hasMore=false` from empty `posts`; the grid hides/disables Load More, and `fetchMore()` returns immediately, never calling page 2. An intermediate empty page has the same effect. A nonempty final page is also falsely marked as continuing until an extra terminal fetch.

#### Evidence and safeguards checked

The session maintains a sequential cursor and correctly preserves source origin; it does not suppress page 2. The grid's `RawPostGrid._buildLoadMore` has a visible button when `controller.hasMore` is true and content cannot scroll, so UI continuation would be possible if the controller honored the metadata. T007/#113 updates the grid's refresh and fetchMore to use `_canLoadMore`, prioritizing explicit `result.hasMore`, which addresses the identified termination. Neither branch is integrated at current `develop` according to remote refs; there is no combined-candidate verification.

#### Root cause and practical impact

A generic grid's old *nonempty-result means more pages* heuristic conflicts with Pixiv's cursor protocol where excluded/invisible posts leave empty result windows. Users can lose access to later Favorites, including when the next cursor is known. This is statically confirmed via the code and its own fixture, not reproduced on a device.

#### Minimal recommended correction

Merge/integrate #113's explicit continuation handling **before or with** #117, or backport the same `hasMore/maxPage/total` policy into the final #117 integration candidate. Avoid a second, Pixiv-specific workaround. Extend the existing fixture to a real `PostScope<Post>` + `PostGrid` widget/integration test, asserting a first invisible/empty page with `hasMore:true` renders reachable Load More and then displays page 2; verify last nonempty page terminates without an extra fetch. Run full grid and Pixiv regressions on final candidate.

#### Assumptions and remaining uncertainty

The fixture proves the empty-page source contract is supported; occurrence frequency on real Pixiv accounts is unknown. #113 appears to resolve this static path but has not been compiled or executed together with #117 in this audit. Do not mark resolved until the fixing code is present in the integrated source and tested.
