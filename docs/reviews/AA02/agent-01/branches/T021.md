## Finding

### AA02-A01-F0003 — Preview safety flags default to allowing a partially specified artwork

- Kind / severity / confidence / lifecycle: **risk / low / suspected / open**.
- Affected issue(s), branch(es), and target IDs: #118; `feature/118-pixiv-following-artists`; T021.
- Origin: introduced in Pixiv artist-card preview projection.
- Reviewed head and comparison SHAs: `1d02bef637966999fbd0b72ecb9c6f0e1eedce8a`; `develop@84df0c2de6cf8fe0177c49babb3fb0eee880f866`; merge-base `422aeae087c1108e655d85d1a3dac25120456cd6`.
- Location: `lib/boorus/pixiv/following/presentation.dart` `pixivFollowingPreviewUrls` L13–22 (especially L16–18); `packages/booru_clients/lib/src/pixiv/types/pixiv_illust_dto.dart` `fromJson` L58, L68–70 and nullable fields L103–114.
- Sources: [filter projection](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/boorus/pixiv/following/presentation.dart#L11-L22), [nullable DTO parsing](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/packages/booru_clients/lib/src/pixiv/types/pixiv_illust_dto.dart#L40-L70).

#### Expected versus observed source behavior

The artist-card preview is meant to respect account content restrictions and omitted/restricted data. However, the filter uses `artwork.visible != false && artwork.isMuted != true && (artwork.xRestrict ?? 0) <= maxRestriction`. It admits *unknown* visibility, mute and age restriction as acceptable, because nullable fields default to unrestricted. `PixivIllustDto.fromJson` explicitly returns null for absent `visible`, `is_muted` and `x_restrict`.

#### Trigger and reachable failure path

When an otherwise valid supplied preview object has an allowed `i.pximg.net` image URL and correct source artist ID but lacks `x_restrict` (or the visibility flag), its thumbnail passes the filter even for an account with `maxRestriction: 0`. A restricted artwork with incomplete metadata **could** appear in a supposedly safe artist preview row. There is no evidence in this audit that the real Pixiv endpoint actually returns such partially specified restricted records.

#### Evidence, safeguards, causes and impact

The existing `pixiv_following_presentation_test.dart` explicitly covers a present `x_restrict: 1` and `visible: false`, not null. The client does not fetch more artworks and requires an allowlisted host, reducing URL exfiltration risk; the account API may itself already suppress inaccessible media. Source condition is confirmed, but actual exposure depends on external response semantics, hence **suspected risk**, *not* a confirmed content leak.

#### Minimal correction proposal

First collect sanitized Pixiv following-list payload samples (including unavailable/private/restricted previews) and confirm whether absent fields are meaningful. If absence is possible, fail closed for unknown age/visibility or apply the verified account/API guarantees deliberately, with explicit tests for null metadata. Preserve no-extra-request policy.

#### Suggested local verification and regression

Mock a preview with omitted `x_restrict` but valid URLs, at account restriction 0/1 and missing `visible`; check expected suppression. Test real R18/private and unavailable art on an eligible account without recording secrets or sensitive images. Run client, widget and provider suites.

#### Assumptions and remaining uncertainty

The Pixiv API might guarantee that incomplete preview responses are already safe; if verified, withdraw this risk with documented samples and no unnecessary strictness.
