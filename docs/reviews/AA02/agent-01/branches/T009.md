### AA02-A01-F0001 — Pool bookmark identity aliases different profiles on the same site

- Kind / severity / confidence / lifecycle: **defect / medium / static-confirmed / open**.
- Affected issue(s), branch(es), target IDs: #68; `feature/group-neighboring-series`; T009.
- Origin: introduced by new typed Pool references.
- Reviewed head and comparison SHAs: `771082d9c58363348d74b97a2da23732cdd921f0`; `develop@84df0c2de6cf8fe0177c49babb3fb0eee880f866`; merge-base `482ae4b1e5fd1e34b344a5c61959a210b8527281`.
- Locations: `lib/core/bookmarks/src/types/pool_bookmark.dart` `PoolBookmark.identity` L62; `lib/core/bookmarks/src/widgets/pool_bookmark_button.dart` `build/_perform` L31–38, L73–87; `lib/core/bookmarks/src/providers/bookmark_provider.dart` `_addPoolsToGroup/togglePoolTarget` L251–302; `lib/core/bookmarks/src/providers/pool_bookmark_provider.dart` `resolvePoolBookmarkProfile` L140–160. Import/storage deduplication inherits the same key.
- Sources: [identity](https://github.com/timberpile/Boorusama/blob/771082d9c58363348d74b97a2da23732cdd921f0/lib/core/bookmarks/src/types/pool_bookmark.dart#L62), [button lookup](https://github.com/timberpile/Boorusama/blob/771082d9c58363348d74b97a2da23732cdd921f0/lib/core/bookmarks/src/widgets/pool_bookmark_button.dart#L31-L38), [toggle](https://github.com/timberpile/Boorusama/blob/771082d9c58363348d74b97a2da23732cdd921f0/lib/core/bookmarks/src/providers/bookmark_provider.dart#L278-L306), [profile resolver](https://github.com/timberpile/Boorusama/blob/771082d9c58363348d74b97a2da23732cdd921f0/lib/core/bookmarks/src/providers/pool_bookmark_provider.dart#L140-L160).

#### Expected versus observed source behavior

A saved Pool/Series must reopen and act under its originating profile. The reference has `origin.profileIdHint`, and `resolvePoolBookmarkProfile` explicitly refuses borrowing another account at the same host. However, `PoolBookmark.identity` comprises only engine type, normalized host, and remote Pool ID. The button similarly looks for any saved reference at that engine/host/ID without checking profile. Persistence, additions, UI membership state and import merge all deduplicate on this incomplete identity.

#### Trigger and reachable failure path

Configure two distinct profiles A and B on the **same** Danbooru host (different account credentials/auth). Save Pool #10 into group G while on A. Open Pool #10 while on B and tap Bookmark. `PoolBookmarkButton._perform` reuses A's Pool object, so `BookmarkGroupPicker.pool` shows A's membership. Toggling already-selected G calls `togglePoolTarget`, finds A's key and invokes `removeBookmarksFromGroup` using A's local ID: **a B-profile action removes A's saved reference**. Trying another group instead appends memberships to the A-origin object, not a B-origin reference. Source profile access thus becomes ambiguous even though resolution remains strict.

#### Evidence and safeguards checked

Test `pool_bookmark_source_policy_test.dart` L29–53 explicitly supports multiple profiles and refuses using another profile when the origin hint is missing. The application routing test `pool_bookmark_flow_test.dart` L316–352 uses **different hosts** and does not challenge two accounts on the same host. Standard picker/provider and import persistence tests use one origin. The strict resolver prevents wrong-account network opening when A disappears but does **not** prevent the wrong-reference removal or group membership collision.

#### Root cause and practical impact

The storage/business identity is less specific than the origin authorization identity. Risk includes cross-account group mutations, inability to maintain separate same-host Pool references, and unintended removal. This is a static reachable path, not a witnessed device reproduction.

#### Minimal recommended correction

Make the typed Pool reference business identity distinguish source-profile/auth identities, ideally incorporating a stable origin profile identifier in the key while retaining a safe behavior for older/missing hints. Update all dedupe maps, Hive validation, import/export merge/preflight, UI lookup and cache/Undo identity consumers **together**; decide an explicit migration for existing references and do not silently rebind orphaned hints. Add two-same-host-profile integration tests for add/remove/Undo/refresh/navigation and backup round-trip.

#### Suggested local verification and regression checks

Use A and B profiles at identical host with different logins, save the same remote Pool to different groups, switch to B and toggle its bookmark; assert A stays untouched and both can navigate under their individual accounts. Repeat after process restart and export/import. Run added `pool_bookmark_*` and related bookmark tests; final-candidate full regression required.

#### Assumptions and remaining uncertainty

Same-host independent profiles are supported by existing config/profile behavior, but the precise intended policy for two references to the same public collection should be decided with the product design. No runtime test has been executed.

### AA02-A01-F0002 — Series grouping is never resolved beyond the first 40 saved Posts

- Kind / severity / confidence / lifecycle: **defect / medium / static-confirmed / open**.
- Affected issue(s), branch(es), target IDs: #68; `feature/group-neighboring-series`; T009.
- Origin: introduced in Series grouping wiring.
- Reviewed head and comparison SHAs: `771082d9c58363348d74b97a2da23732cdd921f0`; `develop@84df0c2de6cf8fe0177c49babb3fb0eee880f866`; merge-base `482ae4b1e5fd1e34b344a5c61959a210b8527281`.
- Location: `lib/core/bookmarks/src/widgets/bookmark_scroll_view.dart` `_warmSeries` L420–446 and `_needsSeriesWarm/_synchronizeEntries` L171–189, L371–389.
- Source: [fixed prefix](https://github.com/timberpile/Boorusama/blob/771082d9c58363348d74b97a2da23732cdd921f0/lib/core/bookmarks/src/widgets/bookmark_scroll_view.dart#L420-L446), [one-time admission](https://github.com/timberpile/Boorusama/blob/771082d9c58363348d74b97a2da23732cdd921f0/lib/core/bookmarks/src/widgets/bookmark_scroll_view.dart#L371-L389).

#### Expected versus observed source behavior

Adjacent bookmarked Posts in a confirmed Series should group when rendered, with a bounded metadata budget. The only membership warming path loops over `entries.whereType<BookmarkPostEntry>().take(PoolBookmarkCapability.membershipBudget)`, where the constant is 40, **regardless of visible/scroll position**. Refreshing uses the same first 40, and there is no viewport continuation/path that admits posts 41+. Therefore saved Posts 41 and 42 sharing a Series remain separate whenever the library has more than forty Posts.

#### Trigger and reachable failure path

Have 42+ saved Posts with IDs #41 and #42 adjacent in the current saved order and known Series membership, scroll to them, and observe that the only batch queried the first forty Posts. Their membership is absent from `_seriesCache`; `projectBookmarkSeries` treats it as unknown and keeps two cards. Scroll never triggers a second batch. Repeated top-level refresh also requests the same first 40.

#### Evidence and safeguards checked

The primitive in `neighboring_series.dart` correctly groups supplied memberships; the issue is upstream metadata admission. Tests `neighboring_series_test.dart` cover pure projection and `pool_bookmark_flow_test.dart` covers only three bookmarked Posts. The hard request cap is an intentional safety requirement, but a per-batch cap need not be a permanent lifetime cap on which visible Posts can group.

#### Root cause and practical impact

A fixed *library prefix* is used as the admission window, instead of a bounded *visible/near-viewport* window. Series display becomes size- and sort-position-dependent, contrary to the agreed projection behavior.

#### Minimal recommended correction

Keep a bounded rate/size and per-source cache, but warm membership for newly visible or near-visible saved Post entries as the viewport moves, invalidate stale result generations, and avoid rewriting rendered anchors. Add a 50+ saved-Post widget test that scrolls to a later adjacent Series and asserts a bounded subsequent lookup and correct projection/selection expansion.

#### Suggested local verification and regression checks

Scroll deep in a 50+ Post library, observe actual membership requests and grouped cards, then change sort/source/profile and enter selection mode. Check request suppression, cancellation, and stable scroll anchor during metadata arrival.

#### Assumptions and remaining uncertainty

No alternative scroll-triggered group membership request was observed in the changed BookmarkScrollView path. This is statically determinable from the inspected controller wiring; visual verification remains outstanding.
