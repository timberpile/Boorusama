### AA02-A04-F0004 — A covered update dialog drops the verified APK and unnecessarily downloads it again

- **Kind / severity / confidence / lifecycle:** defect / low / static-confirmed / open.
- **Affected:** #111, T016, atypical navigation with a separate Flutter route covering a still-mounted update dialog.
- **Origin:** introduced by this branch: success assignment changed from a `mounted` check at the comparison base to `_isCurrent`.
- **Reviewed head/base:** `9ac4dd73b4c505c9c300a0e5fe43bf1ba0d06d07` / `422aeae087c1108e655d85d1a3dac25120456cd6`.
- **Source:** [route guard](https://github.com/timberpile/Boorusama/blob/9ac4dd73b4c505c9c300a0e5fe43bf1ba0d06d07/lib/foundation/app_update/src/widgets/app_update_dialog.dart#L64-L64); [download and verified file assignment](https://github.com/timberpile/Boorusama/blob/9ac4dd73b4c505c9c300a0e5fe43bf1ba0d06d07/lib/foundation/app_update/src/widgets/app_update_dialog.dart#L125-L163); [retry action](https://github.com/timberpile/Boorusama/blob/9ac4dd73b4c505c9c300a0e5fe43bf1ba0d06d07/lib/foundation/app_update/src/widgets/app_update_dialog.dart#L100-L109); [verified file retention](https://github.com/timberpile/Boorusama/blob/9ac4dd73b4c505c9c300a0e5fe43bf1ba0d06d07/lib/foundation/app_update/src/github_apk_downloader.dart#L34-L70).

#### Expected versus observed source behavior

Issue #111 explicitly requires avoiding unnecessary redownloads. A backgroundable download is already in flight when an in-app Flutter route is pushed above the update dialog. The APK download passes the downloader's SHA-256/size verification and returns its private cache `File`, but because `ModalRoute.of(context).isCurrent` is then false, the state deliberately does not assign `_apk`. This is independent of lifecycle foregrounding: the dialog remains mounted but temporarily not the current Flutter route. When the overlay route is popped, `_apk` remains null and pressing the update action starts a second transfer. No explicit cleanup removes the first, valid verified cache directory during this state transition.

#### Trigger, evidence and safeguards checked

1. Start the GitHub APK download in the dialog. Before it completes, push a new Flutter dialog/route above it without disposing it (possible from app navigation/deep link).
2. Complete the asynchronous download and verification. At lines 139–151, the app receives the file but rejects the assignment due to not-current route.
3. The original action sees no APK at lines 100–109 and returns; when the original route becomes current, its button remains in the download state.
4. A later tap repeats ABI selection and download. The existing widget tests only background the Android lifecycle without stacking another Flutter route.

The `_isCurrent` guard is correct before opening install settings or OS installer; it is too strong for retaining a completed verified file.

#### Root cause and impact

The code conflates safe retention of downloaded bytes with safe initiation of OS-visible installation. Impact: wasted bandwidth and abandoned private APK cache file when Flutter navigation overlays the update dialog mid-transfer. Low severity due to narrow trigger; normal Android Settings and foreground returns are not implicated.

#### Minimal fix and regression

Store a verified result whenever mounted and the cancellation token remains active; continue gating permission/install launches on route-current and resumed state. Handle route return explicitly or allow a later tap to install the retained file, and clean superseded update cache. Add a widget test covering a second Flutter route before download completion and assert only one network transfer when returning; exercise paused/resumed, cancellation, failed integrity and route disposal too.
