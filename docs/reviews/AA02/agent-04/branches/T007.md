## Issue and implementation

The user reported a redundant Load More control when opening already exhausted Related Posts or pool collections. The change makes `PostGridController` prefer trustworthy `hasMore`, `maxPage`, or completed `total` evidence over a simple nonempty response; it retains nonempty final-page posts, reports finite single-page lists as exhausted, and advances pool ID slices based on their deterministic cursor rather than filtered/missing post counts. Failed pool detail queries now propagate their errors.

## Findings

**No additional actionable defect established in this inspected source scope.** The explicit `hasMore` signal takes precedence; `maxPage` is compared to the current page, and a declared `total` is used only when the unfiltered, deduplicated number of loaded posts reaches it. Failed fetches do not mark continuation exhausted. For ID-defined pools, a missing post in the current slice does not suppress remaining slices; final nonempty pages are added before exhaustion is announced.

No guarantee is made that every engine emits authoritative counts. Where no explicit boundary is available, nonempty response fallback intentionally retains the old behavior; the original report may therefore persist for an affected source outside the changed finite/pool paths.
