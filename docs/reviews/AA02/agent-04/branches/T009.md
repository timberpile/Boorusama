## Intended and implemented behavior

A saved Pool is a typed identity + bounded metadata summary rather than its full member post snapshots; it can join multiple Bookmark Groups, coexist with independently saved Post bookmarks, show in mixed grids and full-group previews, and be exported/imported as backup version 6. Direct Pool pages show the ordinary bookmark control. A bounded provider computes cover, indexed tags and optional upload extrema; filter semantics use only stored tags. Confirmed neighboring Series post runs can be projected to a full-remote-count Pool card while selecting restores individual Posts. Danbooru and Szurubooru supply engine-specific capability adapters; source/profile resolution must respect saved origin identity.

#### Expected versus observed source behavior

Under the agreed **source-profile restrictions**, profile A's saved Pool reference should not implicitly become profile B's active Pool bookmark target when accounts share a host but have different authorizations. Yet `PoolBookmarkButton.build` and `_perform` both match a saved pool by Booru type, normalized host and remote Pool ID, **without checking `pool.origin.profileIdHint` against `config.id`**. Both profiles therefore show the same badge; opening the picker from B hands it A's saved `PoolBookmark` rather than fetching a B-scoped draft. Toggling its group operates on A's existing site-level entry.

#### Trigger and reachable failure path

Save Pool #N with private-access profile A on `host.example`; switch to another configured account B on that host and visit its same numeric Pool ID page. The button's finder selects A's reference, even though the strict `resolvePoolBookmarkProfile` resolver deliberately refuses borrowing a different account for opening/refreshing. `BookmarkGroupPicker.pool` sends this old reference to `togglePoolTarget`, which resolves by the site-level `identity` and may **remove a group membership of the A-owned bookmark**. If B's view has different availability/visibility, the badge and action do not reflect B's profile.

#### Evidence and alternative explanations checked

This is a local source-state trace, not a credential leak or runtime reproduction. The site-level identity was intentionally chosen to prevent duplicate Pool IDs per source, and global bookmark reuse across accounts on one host may be deliberate. However, the same feature documents origin-hint isolation and the implementation includes a strict resolver explicitly protecting account-bound Pool navigation. Existing source-policy tests cover deleted original hinted profiles and different hosts, not two simultaneous accounts on the same host. **If the site-global identity is an explicit product decision**, clarify that contract rather than splitting stored identities unilaterally; the UI currently gives no indication that it is modifying A's saved source record from B.

#### Root cause and impact

Source identity and authorization identity are conflated in the Pool-detail bookmark action. The mismatch may show false bookmark state, reuse stale account-scoped metadata, and unexpectedly remove/mutate group memberships originating from another account. The group-removal Undo mechanism offers potential recovery but does not eliminate the incorrect-account action.

#### Minimal recommended correction

Define the intended cross-account site-level bookmark policy explicitly. Prefer refusing an implicit match to a saved reference with a different, non-null `profileIdHint` and explaining that the existing Pool belongs to the original account. If independent account-specific bookmarks are required, profile identity must be represented consistently in stored identity, all repository deduplication, backup/import and UIs—not changed in one button alone. Add a same-host dual-account widget/notifier test exercising saved-state badges, add/remove, invalidation and navigation under both profiles.

#### Suggested local verification and regression checks

Two configured Danbooru accounts sharing a host; Pool #N saved under account A, then profile B sees the same page, toggles a group and returns to A. Inspect both badge and persisted `origin.profileIdHint`, membership delta and open/refresh requests; repeat with A removed and B still present, restricted/private Pools, and backup/restore. Verify that no hidden network or account borrowing occurs. Local emulator credentials must not be recorded in evidence.

#### Assumptions and remaining uncertainty

The source trace demonstrates a same-host account mismatch; whether separate saved identities are *required* must be clarified with the user. Impact on private Pools depends on host account permissions. Classified **high-confidence**, not static-confirmed, for the unverified product policy and multi-account reachability. No device reproduction.
