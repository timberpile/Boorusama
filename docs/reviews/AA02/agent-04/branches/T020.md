## Issue and implementation

Pixiv Favorites now uses the common navigation, profile picker, Post Grid and Viewer with Public/Private filters and cursor pagination. The client extracts a validated strictly decreasing `max_bookmark_id` cursor from the server's `next_url`, but **does not** request the server-supplied URL. The session binds Post origins, cancels on scope disposal, exposes `hasMore`, preserves final-page posts and keeps account/filter sessions isolated. No write action is introduced and unverified All/Bulk Match are not advertised.

#### Expected versus observed source behavior

The Pixiv endpoint can return bookmarks whose `visible:false` or muted/restricted illustrations are excluded from local Post conversion; its `next_url` still supplies a valid decreasing cursor. The newly introduced `PixivFavoritesSession` correctly returns an empty `PostResult.posts` **with `hasMore:true`**, as covered by its added session test. But the shared `PostGridController` on this branch sets `_hasMore = newItems.posts.isNotEmpty`, ignoring the authoritative `PostResult.hasMore`, both after first-page refresh and subsequent `fetchMore`. For an empty result, the controller exposes no more data and the UI cannot reach later valid favorites.

#### Reproduction path

1. Pixiv `user/bookmarks/illust` returns a page of restricted/invisible art and a valid `max_bookmark_id` continuation. `illustDtosToPosts` filters them all.
2. `PixivFavoritesSession._fetch(1)` or `_fetch(n)` advances its cursor and correctly produces `posts=[]; hasMore=true`.
3. The new Favorites Page binds the session to the unmodified shared `PostScope<Post>` infinite grid.
4. `PostGridController._performRefresh` or `fetchMore` overwrites `hasMore` with `posts.isNotEmpty` = false, regardless of the session's valid cursor.
5. Both automatic `InfiniteScrollListener` and fallback Load More button depend on `controller.hasMore`. On a blank first page the button disappears, and after a later blank page further results cannot be requested. Subsequent favorites remain hidden.

#### Safeguards and alternatives checked

The #117 tests specifically include a restricted first page that returns no posts but reports `hasMore:true`; however they test only `PixivFavoritesSession`, not a mounted `PostScope/PostGridController`. The branch's shared controller is unchanged from the merge-base. The separate #113 branch corrects it using `_canLoadMore`, which preferentially checks explicit `result.hasMore`, but that branch is independent and not included in T020's pinned source. This is a source-proven integration defect, not a Pixiv cursor or security error.

#### Root cause, impact and minimal correction

The grid conflates filtered display emptiness with server pagination exhaustion. Fix the shared controller's end-of-stream logic using authoritative `PostResult.hasMore` and preserve final nonempty pages (as explored by #113), rather than swallowing the Pixiv cursor or guessing `total`. Before integrating, reconcile #113's changes against current `develop`; do not blindly cherry-pick an old branch. Keep bounded, nonrecursive pagination and a manual Load More affordance for a blank viewport with a valid cursor.
