## Implementation summary

The branch exposes a read-only Pixiv Favorites page through `PixivBuilder.favoritesPageBuilder` and the shared Favorites profile picker. It offers Public/Private filters, a `PostScope` configured for infinite pagination, and a `PixivFavoritesSession` keyed by account/filter with generation cancellation. The Pixiv client adds the fixed authenticated `/v1/user/bookmarks/illust` API endpoint, validates `next_url` as a same-origin, same-account, same-visibility, strictly decreasing numeric cursor, and *only* extracts the cursor; the server-supplied URL is not followed. Navigation availability requires a refresh token and a positive stored Pixiv account ID. Pixiv post parsing and origin binding are reused.

#### Expected versus observed source behavior

Expected: a Pixiv Favorites API page containing only restricted/deleted works should yield zero visible posts but retain the next cursor when the API still advertises more pages. Observed source: `PixivFavoritesSession` correctly returns `PostResult(posts: [], hasMore: true)` in this case (its own test creates exactly this scenario). However, this branch's `PostGridController._performRefresh` ignores `result.hasMore` and assigns `_hasMore = newItems.posts.isNotEmpty`, so it disables further fetches. `fetchMore` repeats the same condition for intermediate empty pages, losing the rest of the feed. The user's Favorites page remains at the empty prefix with no way to request later pages by scrolling.

#### Trigger and reachable failure path

Open shared Favorites for a Pixiv account/filter whose first or intermediate returned API page contains only hidden, muted, deleted or otherwise unresolvable items while `next_url` is valid and non-null. Pixiv parser filters those items to empty; session carries `hasMore: true`; grid marks exhaustion and cannot load following cursor pages. The branch's isolated session test proves the relevant response contract exists but does not exercise the grid integration.

#### Evidence and safeguards checked

The page uses the unmodified shared `PostScope<Post>`, `pageMode: PageMode.infinite` and `fetcher: session.getPosts`; no wrapper retries filtered pages. `PostGridController.fetchMore` has an early return when `!_hasMore`, preventing recovery. #113 updates the shared controller to prioritize explicit `hasMore` and ingest terminal nonempty results, but #117's branch has not incorporated that diff. The issue handoff acknowledges the dependency; that acknowledgment does not make the independent branch functional in this case.

#### Root cause and practical impact

The shared grid conflates an empty *visible* page with source exhaustion; account- and visibility-scoped cursors are lost despite correct source pagination metadata. Users with restricted/private collections may see empty or truncated Favorites.

#### Minimal recommended correction

Integrate/rebase #117 only after a verified #113-compatible `PostGridController` is present, or introduce a narrowly-scoped equivalent continuation contract; do not add silent/unbounded auto-fetches or fake offset-based page jumps to the cursor adapter. Preserve #117's bounded sequential session and host validation.

#### Suggested local verification and regression checks

Add a shared-grid/provider widget test with first page `posts: []`, `hasMore: true` and second page with real posts, then verify scroll/fetch reaches the second cursor; repeat for a nonterminal empty intermediate page and a nonempty terminal page. Test both Public and Private, profile switching mid-request and denied token refresh, and run combined #113 + #117 full candidate regression and Android acceptance.

#### Assumptions and remaining uncertainty

No live Pixiv feed was queried; failure is statically demonstrable given the branch's own accepted restricted-only source-page scenario. #113's isolated fix has not been integrated or runtime-tested as the joint state; it is a plausible corrective dependency, not an integrated resolution. Finding remains open until observed source includes a tested fix.
