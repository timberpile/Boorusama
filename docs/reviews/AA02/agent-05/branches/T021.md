## Implementation summary

The branch adds `pixiv.following-artists` as an account-gated Pixiv-specific navigation tool, routed to a read-only artist list scoped to an explicit originating profile. The fixed Pixiv API endpoint is `/v1/user/following`, with Public/Private and validated forward-only `offset` pagination. The client never follows supplied next URLs; an account/filter-scoped autoDispose Riverpod AsyncNotifier coalesces load-more requests and cancels obsolete requests. Artist cards use the supplied avatar, name/account and up to three already-supplied preview images, and open the normal search page with the numeric `user:<id>` query and original config. Existing global Following Topics data is untouched.

### AA02-A05-F0003 — Following Artists previews bypass explicit-content cover

- **Kind / severity / confidence / lifecycle:** `defect` / `medium` / `static-confirmed` / `open`.
- **Affected issue(s), branch(es), and target IDs:** #118, `feature/118-pixiv-following-artists`, T021.
- **Origin:** `introduced`; the new artist card is a separate image surface with no existing grid-level explicit-content wrapper.
- **Reviewed head and comparison SHAs:** `1d02bef637966999fbd0b72ecb9c6f0e1eedce8a`, merge base `422aeae087c1108e655d85d1a3dac25120456cd6`, develop `84df0c2de6cf8fe0177c49babb3fb0eee880f866`.
- **Location:** `lib/boorus/pixiv/following/artist_card.dart`, `PixivFollowingArtistCard.build` lines 16–57; `lib/boorus/pixiv/following/presentation.dart`, `pixivFollowingPreviewUrls` lines 10–22. Missing shared behavior in `lib/core/posts/post/src/widgets/explicit_block_overlay.dart` and `lib/core/posts/listing/src/widgets/post_grid_item.dart`.
- **Source:** [new card](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/boorus/pixiv/following/artist_card.dart#L16-L62), [preview filter](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/boorus/pixiv/following/presentation.dart#L10-L22), [shared explicit-content control](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/core/posts/post/src/widgets/explicit_block_overlay.dart#L1-L108), [grid integration](https://github.com/timberpile/Boorusama/blob/1d02bef637966999fbd0b72ecb9c6f0e1eedce8a/lib/core/posts/listing/src/widgets/post_grid_item.dart#L213-L247).

#### Expected versus observed source behavior

Expected: when `imageListingSettingsProvider.mediaBlurCondition == MediaBlurCondition.explicitOnly`, an explicit/R18 artwork thumbnail should remain covered until the user explicitly reveals it, including in newly added preview collections. Observed: the standard grid wraps each post in `ExplicitContentBlockOverlay(rating: post.rating)`; the new Following Artists card renders allowed artwork preview URLs directly through `BooruImage`, without checking the user's blur setting or applying the shared overlay. The only restriction is server visibility/artist and `artwork.xRestrict <= account.xRestrict`, which is not the user's local media blur preference.

#### Trigger and reachable failure path

Authenticate to a Pixiv account that permits R18 content (`account.xRestrict >= 1`), enable the app's explicit-content blocking preference, and open Following Artists for an account whose supplied preview has `x_restrict == 1`. The preview passes `pixivFollowingPreviewUrls(... maxRestriction: account.xRestrict)` and the card paints the image with no explicit block. This violates the same user's expectation from the Post Grid; no additional source fetch is necessary.

#### Evidence and safeguards checked

`PixivFollowingArtistCard` does not use `PostGridItem` and never constructs `ExplicitContentBlockOverlay`. The shared `BooruImage` controls general automatic media loading but does not itself implement explicit rating-based covering. `pixivFollowingPreviewUrls` checks `visible/isMuted/xRestrict`, not the imageListing blur setting; allowing R18 by account capability is intentional, but does not override an explicit user cover setting. Current presentation tests only prove rejection with `maxRestriction: 0`, not the permitted-R18/blur-enabled combination.

#### Root cause and practical impact

A new card bypasses the app's centralized post-media presentation wrapper, so explicit previews can appear without the user's chosen cover in a page listing multiple artists. Privacy/content preference mismatch is user-visible and potentially sensitive.

#### Minimal recommended correction

Use the existing `ExplicitContentBlockOverlay` (or its shared equivalent) around each artwork preview, deriving the rating from Pixiv metadata such as `xRestrict` and sanity level. Preserve the already verified account restrictions, no-extra-requests rule and up-to-three-card layout. Do not apply an unconditional blur to the artist avatar/name.

#### Suggested local verification and regression checks

Add a widget test with `x_restrict=1`, account permission 1, local `MediaBlurCondition.explicitOnly`, verifying the preview is covered until revealed; test unrestricted work unaffected, missing ratings, profile changes, 320dp and 2x text. Verify normal post-grid behavior is unchanged. Run provider/presentation tests and full candidate regression.

#### Assumptions and remaining uncertainty

The source path is definite, but user/device reproduction was not conducted. Exact Pixiv endpoint distribution of R18 preview metadata and visual contrast of the chosen cover remain for live/manual validation.
