## Finding

### AA02-A02-F0001 — More menu closes on benign action-list rebuilds

- Kind / severity / confidence / lifecycle: **risk / medium / high-confidence / open**.
- Affected issue/branch/target: #112, `feature/112-viewer-toolbar-layout`, T012.
- Origin: introduced by the configurable toolbar, not the legacy menu.
- Reviewed target head: `8213b6fbb87cb09d30d5056ad6667821371f22f6`; comparison develop `84df0c2de6cf8fe0177c49babb3fb0eee880f866`, merge-base `422aeae087c1108e655d85d1a3dac25120456cd6`.
- Location: `lib/core/posts/details_parts/src/toolbars/customizable_post_toolbar.dart`, `_ConfiguredPostToolbarState.didUpdateWidget`, approximately L99–L109, and `lib/boorus/danbooru/posts/details/src/widgets/danbooru_post_action_toolbar.dart` L50–L79.
- Source: [pinned close condition](https://github.com/timberpile/Boorusama/blob/8213b6fbb87cb09d30d5056ad6667821371f22f6/lib/core/posts/details_parts/src/toolbars/customizable_post_toolbar.dart#L99-L108), [reactive Danbooru parent](https://github.com/timberpile/Boorusama/blob/8213b6fbb87cb09d30d5056ad6667821371f22f6/lib/boorus/danbooru/posts/details/src/widgets/danbooru_post_action_toolbar.dart#L50-L79), [explicit close regression test](https://github.com/timberpile/Boorusama/blob/8213b6fbb87cb09d30d5056ad6667821371f22f6/test/core/posts/details/configured_post_toolbar_test.dart#L195-L229).

#### Expected versus observed source behavior
A displayed More menu should not disappear because an unrelated provider recomputes a favorite/vote badge while the viewer still displays the same post/profile and available actions. The new widget calls `_menu.hide()` whenever `oldWidget.buttons != widget.buttons`. Dart List equality is identity by default. Both real parents allocate a fresh `buttons: [...]` list on each build; therefore a plain parent rebuild, without action identity or authorization changes, satisfies the close condition.

#### Trigger and reachable failure path
Open More for a Danbooru post while `favoriteProvider` or `danbooruPostVoteProvider` is still loading; when that watched value publishes, `DanbooruPostActionToolbar.build` runs again with a new button list. The configured child retains its post/profile key, receives the new list and closes the menu. A subsequent unrelated update repeats the interruption. Standard viewer favorite state has a similar path.

#### Evidence and safeguards checked
The menu deliberately closes when callbacks change to avoid stale source/account actions, and a changed-source widget test explicitly asserts that behavior. The wrapper also keys by post/profile, and its overlay captures the provider container. These guard against stale actions, but the broad **list-identity** check does not distinguish a benign state refresh from a new post/profile or new action availability. This is an observable static path and an interaction risk, **not a device reproduction**.

#### Root cause and practical impact
Over-broad menu invalidation on allocated list identity can dismiss a popup between the user's opening gesture and their intended tap, particularly during asynchronous status loading. This makes menu actions less reliable without conferring additional protection for benign same-profile value changes.

#### Minimal recommended correction
Retain explicit close on post/profile change and actual action-set/authorization change. For stable action identities, update menu item state/callbacks reactively without dismissing; protect in-flight mutations by validating current account at invocation. Replace the existing test with separate cases for benign provider refresh (stays open) and actual post/profile/capability change (closes). If callback ownership cannot be safely updated, document/accept the trade-off instead of silently weakening source checks.

#### Suggested local verification and regression checks
Widget: open More; publish favorite/vote async status; assert it remains visible and renders current label/state. Switch profiles/post while open; assert old menu closes, and old callbacks cannot act on a new profile. Android: fast open→tap under slow network and offline status changes.

#### Assumptions and remaining uncertainty
The callback-change test reveals intentional conservative invalidation; product may deliberately accept this interruption for security. No device evidence quantifies frequency or impact. Hence classified a **risk**, not a static-confirmed functional defect.
