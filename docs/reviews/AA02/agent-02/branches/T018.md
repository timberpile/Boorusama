## Finding

### AA02-A02-F0002 — Series metadata is never fetched beyond the first 40 bookmarked Posts

- Kind / severity / confidence / lifecycle: **defect / medium / static-confirmed / open**.
- Affected issue(s), branch(es), and target IDs: #68, `feature/group-neighboring-series`, T018.
- Origin: introduced by this feature branch's bounded series discovery path.
- Reviewed target head and comparison SHAs: `771082d9c58363348d74b97a2da23732cdd921f0`, develop `84df0c2de6cf8fe0177c49babb3fb0eee880f866`, merge-base `482ae4b1e5fd1e34b344a5c61959a210b8527281`.
- Location: `lib/core/bookmarks/src/widgets/bookmark_scroll_view.dart`, fetcher L174–L189, `_synchronizeEntries` L365–L389, `_warmSeries` L420–L445 and `_mixedGrid` L558–L595.
- Source: [bounded first-40 iteration](https://github.com/timberpile/Boorusama/blob/771082d9c58363348d74b97a2da23732cdd921f0/lib/core/bookmarks/src/widgets/bookmark_scroll_view.dart#L420-L445), [one-shot scheduling](https://github.com/timberpile/Boorusama/blob/771082d9c58363348d74b97a2da23732cdd921f0/lib/core/bookmarks/src/widgets/bookmark_scroll_view.dart#L365-L389), [grid scrolling/rendering](https://github.com/timberpile/Boorusama/blob/771082d9c58363348d74b97a2da23732cdd921f0/lib/core/bookmarks/src/widgets/bookmark_scroll_view.dart#L558-L595).

#### Expected versus observed source behavior
Per issue #68 and current design, adjacent visible already-bookmarked Posts in a confirmed Series can be rendered as a Series card without selecting the whole remote pool. A bounded *request batch* is appropriate, but the current implementation turns the batch limit into a permanent prefix limit for the entire library: only the first `membershipBudget=40` Post entries in the current ordered list can ever receive `getBookmarkSeries` metadata during that load.

#### Trigger and reachable failure path
Open an unfiltered All Bookmarks or Group view with 42+ saved Post entries, with entries 41 and 42 belonging to a known common Series and missing membership cache. Page 1's fetcher materializes *all* entries and sets `_needsSeriesWarm=true`. `_synchronizeEntries` schedules one `_warmSeries` call and sets the flag false. That method iterates `entries.whereType<BookmarkPostEntry>().take(40)` **before** checking cache; it never considers 41+. Scrolling builds later grid tiles but does not schedule another series warm. As a result, those neighboring posts remain independent forever during that view session, despite the Series being discoverable and even when no network request is in flight. Refresh/search-clearing merely reprocesses the same first 40.

#### Evidence and safeguards checked
The widget holds a 10-minute cache and caps concurrent profiles to four; it can queue a new warm only when another full invocation occurs, but no later-prefix/viewport invocation is scheduled. Full tested projection helper `projectBookmarkSeries` can group later posts *given memberships*; this defect is upstream discovery starvation, not the pure grouping algorithm. Existing `neighboring_series_test.dart` and `pool_bookmark_flow_test.dart` cover adjacency and normal warming but have no case with a Series beginning beyond the 40th saved Post. The document only bounds work; it does not exclude visible items after a prefix.

#### Root cause and practical impact
The code treats a **per-request safety budget** as a fixed lifetime library prefix and never advances a window. Large bookmark libraries silently lose the advertised visual Series grouping beyond the 40th Post, including when the viewport scrolls to them. This is demonstrable from reachable source, not a runtime-reproduced claim.

#### Minimal recommended correction
Bound discovery by **visible viewport range or incremental per-page/scroll windows**, preserving request budget, profile count cap, deferred/frozen visible layout and generation cancellation. Skip cached entries before filling the budget. Trigger further bounded discovery only when subsequent saved Posts become relevant, rather than scanning the entire library or silently fetching unbounded pages.

#### Suggested local verification and regression checks
Add a widget integration test with >45 stored Post bookmarks: two adjacent Series members at positions 41/42 must group after scrolling into view, while positions 1–40 still honor the per-request limit and existing cover/profile guards. Check large libraries, partially cached prefix, scroll back/up, filter resets, selection-mode expansion, and no extra network while user stays on initial viewport.

#### Assumptions and remaining uncertainty
This finding assumes the current issue/design requirement applies to all adjacent visible saved Posts, not a documented first-40-only UI trial. Source inspection proves absence of a later window; network response correctness and device UI were not executed.
