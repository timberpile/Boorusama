#### Expected versus observed source behavior

Pixiv can return a page of illust DTOs that are all restricted/hidden/unviewable but with a non-null `next_bookmark_id`. `PixivFavoritesSession._fetch` correctly builds `PostResult(posts: [], hasMore: true)` after `illustDtosToPosts` filters them. The **actual** `PostGridController._performRefresh` ignores `hasMore` and sets `_hasMore = newItems.posts.isNotEmpty`, i.e. `false`. The on-scroll `fetchMore` immediately returns if `!_hasMore`, even though a valid server cursor is available.

#### Trigger and reachable failure path

Open Pixiv Favorites Public or Private under a valid logged-in profile. First source page contains only inaccessible/deleted/muted works, while another cursor page has visible works. Session and its included fixture can create this state; PostScope constructs the unmodified controller; controller marks the list exhausted after the first empty transformed page. The UI shows an empty or incomplete Favorites result with no way to advance automatically to the next cursor. The same can happen on later all-filtered pages because fetchMore also sets continuation from `posts.isNotEmpty` alone.

#### Evidence and safeguards checked

Explicit `result.hasMore` is propagated correctly through Pixiv session and `PostResult`; the screen forces infinite mode; controller's pre-#113 continuation ignores this metadata. The session test inspects its own `hasMore=true` but never mounts the controller and cannot detect the integration failure. #113's **separate unmerged branch** [introduces `_canLoadMore`](https://github.com/timberpile/Boorusama/blob/a1bc1d42903861a46e7230349515946bae678357/lib/core/posts/listing/src/widgets/post_grid_controller.dart#L381-L391), which prioritizes `hasMore`; do not claim integrated resolution.

#### Root cause and practical impact

The older grid uses the number of filtered display Posts as its exhaustion signal. Cursor-bearing sources require source-level continuation independently of how many display Posts survived parsing. Users can miss later visible Pixiv favorites or receive a misleading empty page. This violates explicit pagination/restricted-content requirements.

#### Minimal recommended correction

Integrate and verify #113's safe continuation handling (or equivalent `hasMore`-first logic) before accepting #117; do not add Pixiv-specific paging state to the shared Grid. Ensure a nonempty **terminal** page is also retained, as #113 addresses. Reconcile branch drift, no blind cherry-pick.

#### Suggested local verification and regression checks

Build a PostScope/PostGrid integration test using source pages: first fully filtered with `hasMore=true`, second visible and terminal; assert a real second fetch and visible result. Repeat with later empty duplicate/muted pages and errors/retry. Run existing pagination, Pixiv API package tests and session tests via FVM; authenticate against a real Pixiv account only in a safe local environment.

#### Assumptions and remaining uncertainty

Reachability of an all-filtered real source page depends on account data, but code admits this case and explicitly tests it at session level. Source failure mechanism is deterministic. Not reproduced on a live account or emulator. Fix in #113 remains pending integration.
