### AA02-A03-F0005 — Pool source filter matches hostname substrings

- Kind / severity / confidence / lifecycle: **defect / low / static-confirmed / open**

- Pinned links: [Pool source predicate](https://github.com/timberpile/Boorusama/blob/771082d9c58363348d74b97a2da23732cdd921f0/lib/core/bookmarks/src/types/bookmark_grid_entry.dart#L55-L68), [source option values](https://github.com/timberpile/Boorusama/blob/771082d9c58363348d74b97a2da23732cdd921f0/lib/core/bookmarks/src/providers/local_providers.dart#L63-L83), [source selector](https://github.com/timberpile/Boorusama/blob/771082d9c58363348d74b97a2da23732cdd921f0/lib/core/bookmarks/src/widgets/bookmark_booru_type_selector.dart), [older Post filter](https://github.com/timberpile/Boorusama/blob/771082d9c58363348d74b97a2da23732cdd921f0/lib/core/bookmarks/src/providers/bookmark_group_selectors.dart#L162-L171).

#### Expected versus observed source behavior

The Source selector lists exact host values produced by `availableBooruUrlsProvider`, so selecting `booru.example` should only display bookmarks whose normalized source host equals `booru.example`. The new Pool selector uses `('https://${pool.origin.sourceHost}').contains(selectedBooruUrl)`, which also accepts `notbooru.example`. Both are distinct, syntactically valid hostnames. If Pool references for these two hosts are present, the selected-source grid includes an unrelated Pool reference.

#### Trigger and reachable failure path

Save Pools in two configured endpoints with overlapping hostname substrings, choose the shorter host from the standard Bookmark source dropdown, and inspect `selectBookmarkGridEntries` → `selectPoolBookmarks` → mixed display. The predicate accepts a substring despite different Pool remote identities. Ordinary Post bookmarks are affected by the older analogous predicate. No cross-source fetch or credential transfer is proven; impact is local result correctness and possible inappropriate cached cover visibility.

#### Evidence and safeguards checked

Source menu values are host strings, not arbitrary text queries, so an exact comparison is feasible. `PoolBookmark.identity` and profile reopening do compare canonical source hosts; those safeguards do **not** apply to the display filter. Filtering does not compare booru engine either, matching the existing host-based UI design. The problem is deterministic from valid source inputs, but likelihood depends on hostnames users configure; low severity.

#### Root cause and practical impact

A substring check borrowed from the pre-existing Bookmark Post selector was applied to new Pool references instead of source host equality. The Bookmarks grid can show wrong-host saved Pool tiles under a chosen source, undermining filtering expectations.

#### Minimal recommended correction

Compare normalized canonical hosts exactly in both Pool and Post selectors, using a single helper if one already exists in the repository. Preserve explicit port and engine/profile behavior as existing host selectors intend; no UI redesign. Add a small unit test with two hosts where one contains the other and both Post and Pool references.

#### Suggested local verification and regression checks

Run source-selector/Bookmark search tests via FVM, then filter mixed saved Post/Pool entries across host overlap, same-host different ports and subdomains, both exact host choices, and group filters. Ensure source/profile opener still resolves original origin.

#### Assumptions and remaining uncertainty

Both sites must be configurable and contain saved Pool references; actual user data not observed. The string predicate mismatch is demonstrable at the reviewed SHA; not reproduced on device.
