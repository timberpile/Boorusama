# Experimental video-to-GIF prototype

The user approved `ffmpeg_kit_flutter_new_min` and an Android-only testable prototype on 2026-10-07. Version **3.6.7** is pinned in the lockfile (Android native dependency `com.antonkarpenko:ffmpeg-kit-min:2.2.3`). The previous candidate-selection and platform-approval gates are superseded for this prototype.

On Android, the **GIF** row in the Media section of the post Share dialog sits below Video and matches its tile styling. It has a leading GIF icon and a single trailing wand action (tooltip: Create GIF), available for videos regardless of length. The action opens the approved editor after downloading and inspecting the source once. It previews the selected clip and offers a movable trim window, independent source-frame and playback-speed sliders with subtle vertical step markers, and **360 / 480 / 640 / 720 / Original** dimensions. Numbers cap the longest display edge while preserving aspect ratio; presets at or above Original are omitted. The default is 480 when it reduces the source, otherwise Original. The initial selection covers the full video; either trim edge can shorten it. Original appears last, after the smaller presets; choices wrap onto multiple rows as needed. Source FPS defaults to decoder Original; playback uses eight snapping ratios (25%, 50%, 75%, 100%, 150%, 200%, 300%, 400%) rounded to whole playback FPS, with duplicate states merged. Source and selected-clip duration have no maximum. Encoding still requires a complete supported MP4/WebM with known positive duration, decoder FPS from 1 through 100, and the existing frame-area guard.

The editor keeps the prepared video for adjustment and retry. Its preview remains pinned above the scrolling controls and conversion status; the finished GIF replaces the video in that area. Cancelling conversion returns to the chosen settings. Opening the notification drawer does not cancel GIF preparation or conversion. Encoding and output validation also continue while the app is backgrounded or the screen is off, using an Android foreground service, a temporary partial wake lock, and an ongoing notification with Cancel. The service starts before encoding and stops after all native writers and cleanup finish. Closing the editor cancels native work, which retains its own source owner until writers stop. The result shows measured size and **Adjust**, **Save**, and **Share** on one row, including at enlarged text sizes. Save and Share retain their icons; icons and labels can wrap inside their buttons to fit constrained layouts. Save writes directly to the configured download folder (profile override, then global setting, then the default Download folder), without a destination picker. Share uses the existing owned Android image handoff. Both handoffs retain the GIF while the platform operation is pending, and the GIF preview retains it until image-codec loading finishes when the route closes early.

On Android 10 and newer, public Download/Documents destinations use MediaStore Downloads and Pictures destinations use MediaStore Images. A newly inserted pending row stays hidden until the bounded copy finishes, and partial destinations are deleted on failure. Storage-volume mapping preserves configured subdirectories, including secondary storage. Granted document-tree destinations use URI-based I/O. Older Android versions reserve a fresh filename without overwriting existing files and scan the completed file. Source validation accepts only owned GIFs within app cache or code-cache directories and enforces the same decimal 100-MB ceiling before and during the copy.

The displayed estimate is intentionally coarse: output width × height × rounded selected-source-frame count × **0.5 bytes/pixel/frame**, rounded to decimal MB. The coefficient is uncalibrated and the estimate never blocks creation or runs a trial encode. Playback speed does not change this estimate. Above 20,000,000 estimated bytes, the estimate text and its trailing warning icon turn yellow; this is informational and does not disable creation. There is no quality selector: the encoder uses an adaptive per-frame palette with Sierra2_4a dithering. Only the measured **100,000,000-byte** output ceiling rejects a result; the recovery action retries at the next smaller available resolution and half the original source FPS while preserving trim and speed. If no smaller preset is available, it retains Original dimensions and reduces frames.

The video is downloaded through the existing media preparation with authentication and bypass headers. Media bytes remain outside the API/data request coordinator, following `docs/http_request_coordination.md`; the older item-07 dependency on GIF downloads was incorrect. Cached video reuse remains deferred because the cache has no completeness guarantee.

The adapter probes local files, validates duration/dimensions before decoding, then fully decodes the source with fail-on-error. The selected minimal native FFprobe build omits display-matrix side data in its JSON even though FFmpeg applies it. Android MediaMetadataRetriever supplies missing rotation through a read-only cache-file channel; explicit FFprobe rotation takes precedence. Encoding uses FFmpeg autorotation, explicit output dimensions/SAR, one filter thread, and per-frame palettes to avoid retaining the full animation. Output is decoded by FFmpeg and inspected in an isolate for complete GIF structure, explicit looping, canvas bounds, frames and delays. Temporary GIFs use the existing lease lifecycle. Android's owned image handoff now also accepts completed, correctly named GIF files in `cache/boorusama-share`; its separate owned copy remains readable after the conversion lease is released and expires through the existing age sweep.

## Required backend contract

The native adapter must inspect a fully downloaded MP4 or WebM and report whether it is complete, its duration, decoded dimensions, display rotation, sample pixel aspect ratio, and decoder-derived frame rate. It must reject unknown or nonpositive duration before encoding. It receives a separate destination path, a validated trim interval, output dimensions, and FPS. Encoding must omit audio, preserve aspect ratio, apply rotation, produce a looping decodable GIF, and report progress when available. Cancellation must stop all writes before the adapter returns; the Dart service then removes partial output and its temporary source. The source file is never overwritten. Save and Share use the same prepared-source conversion service.

The Dart slice constrains trims to the known source interval and enforces a 100 MB (100,000,000-byte) output ceiling. Output validation has no frame-count cap derived from a duration limit. It checks a GIF header and requires a structured output report before a lease can escape. A production adapter must read the entire finished GIF and report full-decode success, actual canvas width and height, whether every frame fits the canvas, usable frame count, every frame delay in GIF centiseconds, and an explicit infinite-loop flag. The plan rejects a selected trim unless its retained source FPS and source duration cover at least two complete frame periods (`duration.inMicroseconds × FPS >= 2,000,000`); at 1 FPS, exactly two seconds is eligible and anything shorter is not. The service compares the observed output with the plan: exact canvas and infinite loop, at least two decoded frames unconditionally, frame count within one of the expected sample count, and each delay between the floor and ceiling of 100/encoded-playback-FPS centiseconds. Total frame delay may differ from the requested output duration by at most half a centisecond per frame plus one centisecond, capped at 25 centiseconds (250 ms). This tolerance covers GIF delay rounding without allowing a missing low-FPS frame to shorten an export by a full second. Encoding completion must mean all writers are closed; validation must be read-only. The service re-stats the output after validation and source release. The fake writes a 1x1 single-frame file and supplies explicit stubbed evidence matching the plan only for lifecycle tests; it does not decode or prove the file's semantics. The historical 15 MB target is unused by this editor and does not trigger quality reduction. The verification below covers representative native files and handoff; broader codec/device coverage, memory profiling, and output-quality comparisons remain open. Video downloads currently use the shared preparation service and do not reuse image-cache bytes: a matching signature alone cannot prove that a cached video is complete, and the existing general Share Video path must not expose truncated files. Safe cache reuse needs a backend probe and a cache contract that guarantees completed files.

The provisional Original-FPS safety range is **1–100 FPS**, inclusive. [GIF89a stores frame delay in hundredths of a second](https://www.w3.org/Graphics/GIF/spec-gif89a.txt); values above 100 cannot be represented at their reported cadence, and values below 1 are treated conservatively as unreliable metadata. The legacy fixed-FPS converter can still use 10/12/15 FPS when decoder FPS is invalid. The new editor requires valid Original metadata before offering its slider. This is a metadata guard, not a claim that every supported decoder or player honors 100 FPS accurately. The output plan also rejects a side that would round to zero, any side above **65,535 pixels** (the GIF logical-screen field's 16-bit limit), and decoded source or output frames above a provisional **3840×2160 = 8,294,400 pixels**. Four RGBA frame buffers at that limit represent an estimated **132,710,400 bytes**; the encode request passes a provisional **160,000,000-byte total working-memory budget** to the backend, which must account for its additional allocations and stream frames rather than retaining the whole animation. This is a preflight ceiling, not a measured safe device limit. Original remains available for sources within the budget. Odd dimensions are valid GIF dimensions. The plan carries normalized rotation and required sample pixel aspect ratio; scaled dimensions reflect both, including 90°/270° rotation. Absent, N/A or unspecified 0:1 sample aspect ratio is treated as square pixels; a supplied ratio is parsed and validated. FFmpeg applies display rotation during decoding. Extreme aspect ratios, frame allocation behavior, and memory pressure still need device measurement.

If conversion fails, output deletion and source-lease release are attempted independently. Cancellation wins over a concurrent typed adapter error, with the original error retained as `cause`. Secondary cleanup failures are returned in `GifConversionException.cleanupErrors` without replacing the primary encoder/cancellation/size failure; startup age cleanup remains a later recovery path for orphaned files. If source release fails after a successful encode, the output is also deleted best-effort and the conversion reports storage failure instead of handing out an unmanaged lease. The existing startup sweep removes expired GIFs from the share directory, but app startup currently suppresses sweep errors; observable failure reporting and recovery must be checked when the native path is integrated.

## Remaining work beyond the prototype

- Optional initialization from the viewer playback position; the editor currently starts at zero.
- Quality/size/time comparisons on representative content, HEVC/VP8/VFR and corrupt/truncated input coverage on real Android hardware, and final default choices.
- Device memory and thermal profiling. The historic 160-MB value is a provisional contract budget, not an enforced aggregate allocator limit of the selected native build. Source dimensions are preflight-bounded and encoding streams frames with one filter thread, but this does not prove safe peak memory on all devices.
- Release distribution/license and per-ABI size review; this local prototype is not release approval.
- Non-Android rollout, if later requested. GIF creation is unavailable on other platforms.

## Approved editor implementation, 2026-10-07

Encoding first trims source time and samples the chosen source frames, then assigns centisecond timestamps from the selected whole playback FPS. Setting the filter time base before assigning timestamps prevents duplicate DTS at faster speeds. An explicit final-frame delay prevents the GIF muxer from reusing the original video delay. Above 100 playback FPS, fewer images are retained while keeping the requested speed; the observed frame count and output duration are validated against this effective encoding plan. These timing cases are exercised with real host FFmpeg fixtures, including slow, fast, fractional source FPS, and 60 → 240 playback FPS. The optional five-frame filmstrip is generated once; a thumbnail failure leaves the editor usable.
